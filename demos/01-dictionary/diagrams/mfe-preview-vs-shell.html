Composing a plugin view, and the two things that render it

A plugin declares its views once. The application shell and the dev-only /__preview harness each read the same two declarations and do the placing themselves — which is why the preview cannot show a view the shell would refuse.

What the preview deliberately does not do

  • No registry, so no curation. The shell only renders a plugin an operator approved and a signature verified. The harness renders whatever the working tree declares — that is its job, and it is why a clean preview says nothing about admission.
  • No routing. RouterLink and RouterView are inert stubs. The shell owns the router (BR-AS09), so the preview does not fake one.
  • No sibling plugins. An extension point drawn through the stub API is an empty labelled box. A cross-owner point such as demo-catalog/details-sidebar/v1 can only be exercised in the shell.
  • No lazy loading to observe. The two-stage lifecycle is the shell's mechanism; the preview collapses it, so skeleton rows and pending-region animations never appear.
  • Nothing in the build. The harness is an apply: 'serve' Vite plugin in shared/mfe-preview/, adopted with one previewHarness() line in a plugin's vite.config.js. It adds nothing to remoteEntry.js.
