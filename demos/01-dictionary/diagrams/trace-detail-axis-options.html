Trace detail — request/response axis

Two layout options for the span detail pane. Everything above the pane (toolbar, trace list, waterfall) is unchanged; so are the palette, type scale, and component styles — these come from shared/unifi-theme as-is.

The problem today

The pane splits left/right for identity and headers, then switches to top/bottom for the bodies. The → and ← markers keep asserting a horizontal axis that the bodies have already abandoned, so the eye changes direction halfway down. That switch is the awkwardness — not the sections themselves.

→ requested by
← responded by
→ Request headers
← Response headers
→ Request body ← axis breaks here
← Response body

Option A — one unbroken axis recommended

Carry the split all the way down, so request is always left and response always right, joined by a single continuous seam. Two consequences worth having: the pairs stay row-aligned (a long response body can't drag its request counterpart out of line — each body scrolls inside its own cell), and because position is now reliable, the axis only has to be named once, in the column captions. Every sub-label then drops its prefix — Request headers becomes headers — taking the words "request"/"response" from six repetitions down to two.

Option B — stacked bands

The opposite resolution: drop the columns entirely so the pane reads strictly top-to-bottom, one full-width band per direction, each holding its own identity, headers, and body. Bodies get the full pane width — better if payloads are ever wide or deeply nested. The cost is losing side-by-side comparison: you can no longer read request and response headers against each other without scrolling.

Why A

Both fix the axis break. A is the smaller change from where you are — the two columns you already have simply continue instead of stopping — and it keeps the side-by-side comparison that makes a request/reply pane worth reading. Payloads here are capped at 4 KiB (BR-036) and the pane is wide, so a half-width body column is rarely the constraint. Below 860px both options collapse to the same stacked order, which is effectively B — so B is already the narrow-viewport behaviour of A rather than a competing direction.
