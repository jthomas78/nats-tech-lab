Design discussion · Two aligned write-side persistence patterns

NATS stream - CQRS

Both paths begin with a caller invoking a producer and use the same NATS ingress. The persistence model is the deliberate difference.

Pattern 1 · KV is authoritative aggregate state

Write-side: Aggregate → KV state

A consumed message invokes the aggregate. The resulting state is committed to KV before the input message is acknowledged.

Relationship view

Shared ingress on the right, write-side behavior in the centre, and the caller on the left.

Sequence view

The same components ordered in time. The caller-to-producer entry is visible but remains outside steps 1–6.

Steps 1–6

  1. Publish the message. The caller first invokes the producer. The producer publishes to a subject captured by the input stream and waits for the JetStream publish acknowledgement. This confirms storage, not completion of business processing.
  2. Deliver to the handler. The durable consumer selects matching messages and delivers them to the write-side service. With explicit acknowledgements, a message remains outstanding until the handler acknowledges it.
  3. Load the current state. The handler reads the aggregate’s key from KV, keeping both the stored state and the KV revision. A missing key starts a new aggregate only when the business operation permits creation.
  4. Apply business rules. The handler restores the write-side aggregate and invokes the requested operation. The aggregate validates it and produces the next state; it does not call NATS or KV itself.
  5. Save with a revision check. The handler updates the key using the revision read in step 3, or conditionally creates a missing key. If another writer has changed it, reload and re-evaluate the operation rather than overwriting newer state.
  6. Acknowledge successful processing. After the save succeeds, acknowledge the input message. Redelivery after a save must be recognized as already processed; a revision check alone does not provide this.

Caller and producer are distinct roles. The caller supplies business intent. The producer is the adapter that serializes and publishes the input message.

Retry boundary. Save and delivery ACK are separate operations. A crash between them can cause redelivery, so processing must be idempotent.

Pattern 2 · Canonical JetStream stream is authoritative · KV is rebuildable

Write-side with snapshot: Aggregate → KV state

One canonical JetStream stream is both the write-side input and the authoritative event history. KV stores a checkpoint that shortens aggregate reconstruction.

Relationship view

The write side consumes input and appends accepted events through the same canonical stream. The snapshot remains derived state.

Sequence view

The canonical stream supplies the input and subsequent aggregate history, then receives the newly accepted event before the optional snapshot refresh.

Steps 1–6

  1. Publish the input. The caller first invokes the producer. The producer publishes the input message to the canonical JetStream stream and waits for its publish acknowledgement.
  2. Deliver to the handler. A durable consumer on that same stream delivers the input message to the write-side handler and holds it pending acknowledgement.
  3. Restore from snapshot and canonical history. The handler reads state, aggregate version, last applied event sequence and snapshot schema version from KV, then reads this aggregate’s events after that checkpoint from the same canonical stream. If the snapshot is missing or incompatible, reconstruction begins from empty state.
  4. Apply business rules. The handler restores the write-side aggregate and invokes the requested operation. An accepted operation produces a new domain event; a rejected operation produces no state-changing event.
  5. Commit the event first. Append the accepted event to the same canonical stream with an optimistic concurrency guard and wait for its JetStream publish acknowledgement. A conflict requires reloading and re-evaluating the operation.
  6. Refresh the snapshot when due. Conditionally save the committed state, aggregate version and acknowledged event sequence to KV. The input may be acknowledged after the event commit; snapshot failure must not cause the accepted event to be appended again.

Snapshots accelerate hydration. They are write-side checkpoints, separate from query projections. Snapshot plus subsequent events reconstructs current aggregate state.

The canonical stream remains authoritative. It is also the write-side input stream. Losing KV increases reconstruction work but does not lose accepted history. Keep sufficient event retention for a complete rebuild.

NATS references: consumer delivery and replay, KV revisions and conditional updates, and publish concurrency headers. Snapshot policy and aggregate metadata are application responsibilities.
