How Module Federation
actually works

A shell app draws the frame. Separate apps, built and deployed on their own, ship chunks of finished screen into it while the page is running. Nothing is imported at build time. These eight cards explain the mechanism from the ground up, using the plugins this repository actually builds.

The one-sentence version

Module Federation lets one JavaScript application load code out of another application at runtime, over HTTP, while sharing a single copy of the libraries they both use — so the two can be written, built and deployed by different people at different times.

Read this first if the words are new

A chunk is just a JavaScript file the browser can fetch on demand. A host is the app that asks for one. A remote is the app that offers one. Everything else on these cards is detail hanging off those three words.

How module federation worksCard 01 · The problem
01
Why anybody wanted this

One page, many teams

A browser shows one page. A company has many teams. For twenty years those two facts were reconciled by putting every team's code in one build — which means every team ships when the slowest one is ready. Micro-frontends break that link. Module Federation is the plumbing that makes it practical.

What the single build costs
  • One team's failing test blocks four teams' releases
  • Upgrading a shared library is a company-wide event
  • The build gets slower for everyone, forever
  • Ownership blurs: everything is in everyone's repository
What federation buys
  • A team ships when it is ready, on its own pipeline
  • Adding a feature to the product is a configuration change, not a host rebuild
  • A broken feature can be switched off without redeploying anything
  • The page still feels like one app, because the shell owns the frame
In this repo

The host is lab-shell. The features are the folders under lab-shell/plugins/ — demo-catalog on port 7112, example-plugin on 7111, and three deliberately broken ones used to prove failures stay contained. Each has its own package.json, its own vite.config.js and its own dev server. The shell imports none of them.

The five words you need

Host, remote, container, exposed module, chunk

Every explanation of Module Federation uses these five words in the first paragraph and defines none of them. Here they are, mapped onto two real folders in this repository: the shell at lab-shell/ and the demo plugin at lab-shell/plugins/demo-catalog/.

container a tiny file listing what this plugin offers. Nothing else. E ./plugin — the exposed module maps to src/plugin.js. The only door in; everything else is private. J chunk-*.js — the chunks the actual views and CSS. Fetched only when the plugin is first used. HOST BUILD — lab-shell, port 7110 H lab-shell — the host its vite.config.js declares remotes: {} — an empty list. It is built without knowing any plugin exists. AT RUNTIME — in the browser registerRemotes([{ name, entry, type: 'module' }]) loadRemote('demo_catalog/plugin') fetch, on first use The arrow crosses a network boundary, not a build boundary. That is the whole trick.
Host

The app that asks. Owns the page, the router, the layout. Here: lab_shell.

Remote

The app that offers. Built and deployed alone. Here: demo_catalog, example_plugin.

Container

remoteEntry.js. A menu, not a meal — it names what can be loaded and how.

A naming detail that trips people

The container name is snake_case (demo_catalog) because it can become a global JavaScript identifier in some output formats. The plugin's id stays kebab-case (demo-catalog), and the plugin manifest carries the mapping between the two. They are different names for different layers — do not "tidy" one into the other.

Card 02

Host and remote are roles, not products. One app can be both. In this repo the shell is only ever a host and the plugins are only ever remotes, which keeps the direction of trust easy to reason about.

What a plugin build produces

Six lines of config, and what each one makes

A plugin is an ordinary Vite app with one extra build plugin. This is the whole of lab-shell/plugins/demo-catalog/vite.config.js that matters, and what each key is responsible for in the finished output.

Config keyValue, as builtWhat it produces, and why it is set that way
name'demo_catalog'The container's identity. The host uses this exact string in loadRemote('demo_catalog/plugin'). snake_case, because it can become a global identifier.
filename'remoteEntry.js'The file the host fetches first. It is the plugin's public address — here, http://localhost:7112/remoteEntry.js.
exposes{ './plugin': './src/plugin.js' }The one door in. Everything not listed here is private to the plugin, no matter what it exports.
sharedvue, @primeuix/styled
both singleton: true		Libraries the plugin will borrow from the host instead of shipping its own. See Card 05 — getting this wrong is the classic federation bug.
bundleAllCSStruePuts the plugin's styles inside its chunks, so a loaded plugin arrives already styled. No separate stylesheet for the host to know about.
build.target'esnext'Modern module output. The host must load this as type: 'module' — see the warning below.
What is in the plugin's dist folder
  • remoteEntry.js — small, always fetched first
  • __federation_expose_plugin-*.js — the exposed module
  • chunk-*.js — views, components and CSS, fetched behind it
  • manifest.json — this repo's own metadata file, not a federation file
The manifest is not federation

Module Federation knows nothing about routes, navigation entries or panels. Those live in this repo's own manifest.json and are read by the shell before any federation call happens. Federation only ever answers one question: "give me the code behind this name."

The failure that wastes an afternoon

Vite emits ES modules, so the host must register the remote with type: 'module'. Federation's default is a classic script, which dies on the first import statement with a raw SyntaxError naming neither the plugin nor the cause. It looks like a broken bundle. It is one missing word.

Card 03

A plugin build is a normal build plus a declaration of what it lends and what it borrows. Nothing about the host appears anywhere in it.

How module federation worksCard 04 · Runtime
04
From cold page to mounted panel

The eight steps, in order

This is the whole mechanism. Steps 1 and 2 happen at boot for every plugin. Steps 3 to 8 happen once per plugin, the first time something on screen actually needs it — and never again.

Why steps 1–2 must fetch nothing

A booted shell has a complete navigation tree and a complete route table with zero plugin chunks fetched. Metadata before code. Twenty plugins cost twenty manifest entries at boot, not twenty bundles — so the shell's start-up time does not grow with the product.

What "first use" means in practice
  • A user clicks a nav entry the plugin contributed
  • A page renders an extension region the plugin fills
  • A topbar control or footer item comes into view

Any of these is enough. None of them happens at boot.

Card 04

Federation's only job is steps 4 to 7. Step 1, 2, 3 and 8 are the shell's own work — which is why the shell could swap federation for something else and keep its behaviour (Card 06).

How module federation worksCard 05 · Shared libraries
05
The one setting that breaks everything

Why there must be exactly one Vue

The host is a Vue app. Every plugin is written in Vue. If each one ships its own copy, the page ends up running two Vues that cannot see each other — and the symptoms look nothing like the cause.

Symptoms of a duplicated Vue
  • inject() returns undefined in a plugin component
  • A ref updates but nothing re-renders
  • Theme tokens apply in the shell and not in the panel
  • Console warnings about multiple Vue instances, easily missed
The two settings that prevent it
  • shared: { vue: { singleton: true, requiredVersion: '^3.5' } } in both configs
  • resolve.dedupe: ['vue','primevue','@primeuix/styled'] in the host

requiredVersion is the guard: if a plugin needs a Vue the host cannot supply, federation says so at load time rather than half-working.

The trade this makes

Sharing is what makes a plugin small and the page coherent — but it is also a real coupling. A plugin cannot unilaterally jump to a Vue major version the shell does not run. That is the honest cost of federation, and the reason the shared list is kept short and deliberate: Vue and the theme registry, nothing else.

Card 05

Independent deployment is not independent everything. The shared scope is the seam where the two apps must still agree, so keep it small and write it down.

How module federation worksCard 06 · The seam
06
Keeping federation replaceable

One method, in one file

Module Federation is a choice, not a law. In this repo the whole of it is confined behind a four-line interface, so the shell above it never learns the word "federation" — and could be moved to import maps, or to plain dynamic import, by editing one file.

What the adapter actually does
  • Turns a relative URL into an absolute one against the page
  • Calls registerRemotes once per plugin, tracked in a Set
  • Strips the leading ./ and calls loadRemote('name/expose')
  • Throws a clear error if the remote returns nothing

That is the whole file. Roughly thirty lines.

Why this seam is worth having

Federation is young and the ecosystem moves. Import maps are a browser-native alternative that may make this library unnecessary. Because the shell only ever calls load(remote), swapping is a change to this file plus one line of main.js — not a rewrite of the plugin system.

Failures are named, not raw

Every way a load can fail is mapped to a stage a human can read: remote-not-curated → curation check, chunk-load-failed → remote entry fetch, malformed-module → module resolution, activate-threw → plugin activation, render-threw → contribution render. So "plugin X failed" always comes with "at which step".

Card 06

Wrap the vendor. The interface is four words wide, and it is the reason none of the other seven cards would have to be rewritten if the loading technology changed.

How module federation worksCard 07 · Worked example
07
End to end, one real plugin

From a line of metadata to a panel on screen

example-plugin exists to demonstrate one contribution of every kind. Its manifest.json names components as strings; its plugin.js exports those same names as real Vue components. The string is the only link between them — and it is checked at load time.

Manifest, at boot

Read over NATS from the curated registry. Gives the shell a route, a nav entry and three slot targets — with no code fetched.

Module, at first use

loadRemote returns { components, activate }. activate(shellApi) runs once and hands the plugin a frozen, read-only shell API.

Render

The shell looks up the string in components. Missing name, or a component that throws, fails that one contribution — not the page.

The demo case, in this repo's words

demo-catalog exposes exactly two components — catalog (the demo menu) and intro (a demo's intro page). The shell draws the topbar, the rail and the footer; the demo's own screen arrives as a chunk from port 7112 and mounts inside that frame. To the user it is one application. To the build system it is two, and neither one imports the other.

Card 07

Names in metadata, components in code, matched at load time. The whole plugin contract fits in one sentence because federation is doing only the fetch.

How module federation worksCard 08 · The limits
08
Where the library stops

What Module Federation does not give you

Federation fetches code and shares libraries. That is all it does. Everything a real product needs around that — deciding which code may be fetched, containing it when it misbehaves, and proving where it came from — is the shell's own work, and none of it comes in the box.

Not providedWhy it mattersHow this repo answers it
TrustAny URL federation is given, it will fetch and run.A curated registry served over NATS. The loader will only fetch a URL an operator put on the allowlist.
IsolationA remote's code runs on the host's page, with the host's privileges.A frozen, read-only shell API is the only surface handed to a plugin. Extension regions are host-owned.
ContainmentOne bad component can blank a page.A failing contribution fails alone; the rest of the page renders. Deliberately broken fixtures prove it.
VersioningNothing checks that a plugin fits this shell.Schema and shell-API version checks at validation, before any code is fetched.
ProvenanceA fetched bundle is anonymous.Signing gates — a release that is not owned, is revoked, or is stale is refused at index time.
CapacityUnlimited contributions into one region wreck a layout.Regions declare capacity; over-capacity contributions are refused when the index is built, not when it paints.
When not to reach for this
  • One team owning the whole front end — the coordination cost buys nothing
  • A page where every part ships together anyway
  • An app small enough that the build is not the bottleneck

Federation is the answer to an organisational problem. Without that problem it is just extra moving parts.

When it earns its keep
  • Several teams with genuinely separate release cadences
  • Features that must be switchable without a host deploy
  • Third-party or tenant-supplied UI you must curate rather than trust

All three are true here, which is why the lab shell is built this way.
