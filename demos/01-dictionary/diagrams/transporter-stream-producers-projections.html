Phase 38–39 · ARCHITECTURE-ORGANIZATIONS-TRANSPORTERS §3

The TRANSPORTER stream — producers and projections

The stream is entirely internal to organizations-service: one event-sourced aggregate writes it, one durable consumer reads it, and that consumer feeds three read models.

What the topology fixes in place

  • Exactly one aggregate writes the stream — TransporterProfile. Organization itself is plain Postgres CRUD and never publishes here.
  • Three write sources, one append boundary. Concurrency is enforced in exactly one place: BR-TP20’s ExpectedLastSubjSeq guard. The Temporal path adds stable Nats-Msg-Id {organizationID}:{event}:{attempt}:{step}, so a workflow retry receives the original PubAck rather than a second transition.
  • Two consumer kinds. One ephemeral ordered consumer per command hydrates the write side and is deleted afterwards; one durable projector serves the read side.
  • Three projections from one consumer. Postgres transporter_profiles is canonical, the organizations KV bucket is a non-canonical write-through cache, and compliance_documents receives GIT certificates only when a document repository is supplied because that table is in the service’s own Postgres, not the tenant account.
  • No other service consumes TRANSPORTER. The stream is entirely internal to organizations-service; cross-service reads go through rpc.* / api.* instead.
