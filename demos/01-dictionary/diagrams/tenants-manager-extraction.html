ARCHITECTURE-ACCOUNTS § Phase 35 (implemented 2026-08-18)

Per-tenant connection manager — one shared package, four consumers

What it does: natstenants.Manager[R] owns per-tenant NATS connection lifecycle — discovering a tenant's .creds file, opening one connection on demand, and closing it reactively off notify.accounts.account.{created,suspended,reactivated} — so a browser authenticated into any tenant's account can reach a service directly over api.*. Four services independently re-implemented the same five behaviours over their own per-tenant connections; Phase 35 extracted them into a Go package, not a service — nothing gains a network hop.

Why this shipped as its own phase

  • The duplication was already load-bearing. The observability.creds omission was a real production-shaped bug: two of the three original copies treated a restricted PLATFORM credential as a tenant and opened a connection that could not legally subscribe. It was found by reading NATS server logs, not by a test, and fixed in each file separately, at different times.
  • The module boundary made it non-trivial. Nothing shared code across services before Phase 35 — no go.work, no replace directive anywhere. The first shared package was also the decision about how this repo does shared Go code at all, including the repo-root Docker build-context change every affected service's Dockerfile needed.
  • Sequencing. Extraction happened after refdata-service had already pasted the fourth copy (Phase 32, deliberately, per BR-D40 — "paste rather than block on the unrelated go.work migration"). Phase 35 was the follow-through on that explicit deferral, not a decision made from scratch.
