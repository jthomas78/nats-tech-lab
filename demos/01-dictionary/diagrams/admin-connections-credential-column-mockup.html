What the two options actually trade

  • The NKey is the only stable credential identity; the name is a label. Option B puts it on screen permanently, Option A hides it behind a title tooltip. It matters because two credentials can share a name while being different users — and because the name alone cannot prove two rows are the same credential, which is exactly the question the platform and acme rows raise.
  • Amber marks credential ≠ connection name, not "error". Under the naming scheme a dedicated credential matches its holder's nats.Name(), so a plain row is the healthy case and an amber row means either a shared credential (the four rows above) or the wrong creds file mounted. On today's stack most rows are amber; after the renames only the genuinely shared ones should be.
  • Ephemeral NKeys rotate per browser session. The three websocket rows are minted fresh by mintUserToken on every reconnect, so their NKey is stable only for the life of the tab. Option B shows a value that legitimately changes on refresh — worth knowing before choosing it.
  • The twelfth column has to come from somewhere. The existing eleven already sum to ~1,020px against a narrower content box, so the table scrolls horizontally today. The cheapest reclaim is Lang (80px): it reads go for every TCP row and nats.ws for every websocket row, which the Type badge beside it already says. Dropping it pays for Option A outright and most of Option B.
  • Neither option needs a new NATS call. nats_connections.go:118 already requests /connz?subs=true&auth=true; the fields are decoded away. The raw jwt stays server-side — only the decoded name and the NKey cross to the browser.
