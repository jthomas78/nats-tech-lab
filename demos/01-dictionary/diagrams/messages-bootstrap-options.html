Messages panel bootstrap — bounding the unbounded read

The Messages panel fetches every entry in the pubsub-messages KV bucket on mount, then renders at most 500 of them. The bucket is capped at 15 min / 8 MiB, so the worst case is a multi-megabyte response to display a few hundred kilobytes of it. Four ways to fix that, and where each one cuts.

  • A bounds bandwidth and parse cost, not server work. The handler still walks the whole bucket to know which N are newest — DeliverLastPerSubjectPolicy delivers by subject, not by recency, so there is no cheap "last N" fetch here. What disappears is the multi-megabyte serialise, transfer, and JSON.parse for entries the panel was always going to drop.
  • A touches a shared endpoint, which is the one thing to weigh. /api/kv/buckets/{account}/{bucket}/entries also backs the ships/container/meta inspectors. An optional limit is additive — absent means today's behaviour — so existing callers are unaffected, and the ones with big buckets get an opt-in bound.
  • B is honest but reads as broken. Ingestion is already best-effort (ADR-047 A7): nothing here can recover an envelope that never reached the stream, and the panel says so. But opening Messages on a quiet system and seeing an empty table is a support question, not a design statement.
  • C fixes the symptom at everyone else's expense. The caps exist to bound the panel's visible window; shrinking them to bound a page load means the operator loses history for a reason that has nothing to do with history.
  • D is the right long-term shape and the wrong amount of work now. A bootstrap RPC with real pagination is what this wants at scale — but it duplicates a KV read path that already exists and is already tested, for a panel whose cap is 500 rows.
