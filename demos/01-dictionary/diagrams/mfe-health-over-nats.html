How the registry learns a plugin is alive

Phase 14 left one thing behind: the only reason a plugin container still joins the frontend Docker network is that the registry dials it there with GET /healthz. That probe also needs REGISTRY_HEALTH_ORIGINS, a hand-written map with one entry per plugin. Phase 15 removes the question — the plugin checks itself and publishes the result, and the registry only listens. The same phase adds a catalogue-reset notice, drawn here because it is the second reason a plugin must now listen. Built and verified live at task 15h: the acceptance gate reads the health plane over NATS and finds a curated plugin reporting healthy about itself, a broken one reporting unavailable with cause unreachable, and a killed one reporting absent without ever being withdrawn.

What the drawing settles

  • The chore disappears because the direction reverses. Nobody outside the plugin needs to know how to dial it, so nothing has to be told — the subject is derived from the plugin id that is already inside the signed entry, and REGISTRY_HEALTH_ORIGINS has nothing left to say.
  • The frontend network was only ever there for the probe. The browser has always arrived on the published host port, from outside Docker. Removing the probe removes the network membership, which is the whole of task 15c.
  • The health signal is still HTTP. The loopback GET is not decoration — a report that did not cost a real request would attest that the publisher is running, which nobody asked. BR-AS45's fetch-origin allowlist is a different list and is untouched.
  • A plugin listens now, and that is a genuinely new posture. The grant is the shared reset notice plus the census subject, which is granted ahead of use because adding a grant later costs a bootstrap-operator.sh edit and a docker compose down -v reseed. No wildcard on the plugin side, and bootstrap-operator.sh's “a plugin speaks, it does not listen” comment is rewritten in the same change rather than left contradicting the code.
  • First health push, then announce — tested as a property. The spec asserts what an observer sees: when an announcement reaches the registry, that plugin's health is already known. Known before discoverable — not a line ordering in main.go.
  • The census is deferred, not rejected. A registry that asks everyone on start-up, reconnect or catalogue reset would mirror the announce plane. It is left out for now because the heartbeat already covers every one of those triggers: the census buys latency, not correctness — it turns a ≤15s absent window into sub-second. The call is made after the rest of Phase 15 lands. As built: still deferred — the subject is granted and nothing sends it.
  • Curated plugins report too. demo-catalog is probed successfully today, so it gains a health publisher and a credential granted only its own health token — no announce, no unregister. Curation stays a property of how an entry reached the catalogue, not of whether it can say it is alive. The “not configured” state ceases to exist.
  • The cost is a shared fate that did not exist before. A plugin serving browsers perfectly but with a dropped bus connection now reads as broken, where the two used to be independent. BR-AS60 keeps that from being destructive, and absent (no report inside the 15s freshness window) and unreachable (a plugin said so about itself, and reads as unavailable) stay separate causes so the common case is not mistaken for the rare one. Heartbeat and freshness are one pair — 5s and 15s — raised together or neither.
  • The reset notice is a backstop, not the recovery path. Start-up announcement is what populates the catalogue. The notice earns its keep only when the registry loses its catalogue while plugins keep running — a truncated table, a restored backup — and it is exactly that case where jitter matters, because every surviving plugin would otherwise re-announce at once. The window is carried in the message so the registry can widen it without a redeploy, and clamped by the plugin so nothing on the wire can narrow it to zero.
  • Silence still never withdraws. BR-AS54 is untouched: a plugin that never reports is absent but still registered, and a plugin that ignores a reset notice is simply not re-announced. Neither path reaches unregister.
