Registry announce flow — from a publisher's signed manifest to a browser

A publisher registers its own micro-frontend over rpc.*. Nothing it sends can put code in a browser on its own: the trust table decides whether it is heard, the domain decides what the row becomes, and an operator decides whether it is served.

The five outcomes, and what each leaves behind

  • inserted — an id the store had never seen. Stored pending: recorded, disabled, served to nobody until an operator enables it (BR-AS39).
  • pending — a known id still awaiting review. The record is refreshed and stays out of every shell's document.
  • updated — an enabled dynamic entry moving within its own allowlisted origin. Applied with no review, because the operator already approved that origin (BR-AS40).
  • requeued — the same entry whose remote crossed an origin boundary. Withheld until an operator re-enables it; a new origin is a new decision.
  • ignored — a static entry already owns the id, so curation outranks the announcement, always. Checked first, which is why every preloaded row is untouchable by its publisher.
