ARCHITECTURE-OBSERVABILITY · BR-036 / BR-045 / BR-AC34 / BR-AC36 / BR-051

How an observation reaches the Admin UI

Two near-identical pipelines that differ in exactly one place: whether the projector merges or overwrites. Phase 48 closed the other two — obs.trace.> now carries the same per-tenant LocalSubject remap obs.pubsub.> always had, and trace-request-reply is bounded on measured numbers. Everything else — one export each, one stream over two subject sets each, one durable consumer each, one notify.* nudge each — is the same shape.

The one place the two paths still diverge

  • Merge vs. overwrite. The trace projector does a read-modify-write append keyed by traceId, de-duplicated on spanId, because a trace is assembled from spans that arrive separately. The pubsub projector does a plain Put under _platform.msg.{spanId} — one envelope, one key, nothing to assemble.
  • What used to diverge, and no longer does. Two of the three differences this page originally drew were defects rather than design. obs.trace.> was imported unremapped, which left the Traces panel able to show only a coarse PLATFORM-or-tenant split; Phase 48 gave it the same remap (BR-AC36), and the tenant is now derived from the arrival subject and stored per span, never read from the envelope (BR-051). trace-request-reply was created with no bound at all while the stream feeding it was capped, so the bucket was the only unbounded thing in the path; it is now 15 min / 8 MiB, from a measured 1,638-record seed run rather than a guess (BR-053) — the same bound pubsub-messages carries, so a message and its trace stay cross-referenceable in the two panels.
