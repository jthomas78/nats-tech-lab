MFE plugin system — class, component and sequence views for both render paths

Five UML views of the same system: the types a plugin and its two renderers share, the containers and subjects each path runs on, and the ordered call chains. Left/production is the application shell; right/development is the dev-only /__preview harness. UML's structure is used as-is — class compartments, component boundaries, lifelines and activation bars — drawn in this repo's dark house style rather than UML's own notation.

Reading the five views together

  • The class view is the only place the two paths meet. Figure 1's centre column — src/plugin.js, public/manifest.json, Contribution, ShellApi — is imported by both sides and owned by neither. Every left-hand class and every right-hand class exists to turn that contract into rendered UI; they share no code and never call each other.
  • The component views differ by an order of magnitude in moving parts. Production is eleven containers on two Docker networks with a message broker in the middle (figure 2). The preview is one npm run dev process serving four files on one origin (figure 3). That is the whole reason the harness exists — and the whole reason a clean preview is not evidence that the shell will load the plugin.
  • The sequence views invert the same two steps. The shell fetches a description, validates it, and only then fetches code (figure 4, messages 7 → 9 → 13). The harness fetches code, then a description it does not check (figure 5, messages 8 → 10). Every difference in what each path can catch follows from that one inversion.
  • What the preview cannot tell you is exactly the list in figure 4 that figure 5 has no counterpart for: validateManifest's eight rejection codes, extension-point ownership and capacity, the remote allowlist, Module Federation's shared-scope negotiation against the real host, and every failure code the loader can return. A green preview means the component renders. Only the shell can say the plugin loads.
  • The shell API version is asserted twice, independently. SHELL_API_VERSION in lab-shell/src/shell/versions.js, and a literal 1 in shared/mfe-preview/shellApiStub.js. Figure 1 draws them as two classes with the same stereotype for that reason. If the shell's API ever reaches version 2, the stub is the second edit and nothing enforces it — see BR-AS07's version discipline.
