Organizations (Transporter Registration & Vetting) — system architecture after Phase 38

Scope: this demo's own POC stack only (demos/01-dictionary). Everything in amber is new in Phase 38 — the TransporterProfile aggregate, Temporal, and NATS Object Store. Everything in grey (TradingPartner, Postgres, the NATS core, the frontend) already exists today (Phase 26) and is structurally unchanged, aside from one additive schema widening and one new command noted below.

Reading the diagram

  • No new microservice. TransporterProfile, Temporal orchestration, and the Object Store client all live inside the existing trading-partner-service container as a sibling domain package — a deliberate scope-control decision (ADR-046), not an oversight.
  • Two genuinely different consistency models sit side by side. TradingPartner stays plain Postgres CRUD with row-level locking (SELECT ... FOR UPDATE); TransporterProfile is event-sourced with optimistic concurrency via Nats-Expected-Last-Subject-Sequence-Subject (ADR-049). The Activate guard is the one place these two models meet.
  • Temporal's own workflow history and the JetStream event log are two separate durable logs describing the same saga. Every publish the workflow triggers goes through a Temporal Activity carrying Nats-Msg-Id, so an Activity retry after a crash never produces a duplicate event (ADR-047).
  • Document bytes force a new ingress. Phase 33.5 removed every REST route from this service; Phase 38c has to reintroduce one dedicated HTTP endpoint purely to proxy Object Store bytes, since NATS micro JSON request/reply can't stream and has no presigned-URL equivalent (ADR-048).
  • Compensation is additive, never a rewrite. If GIT verification fails after documents were already approved, the workflow appends new events (DocumentApprovalReverted, FleetAvailabilityRevoked) rather than erasing the approval — the event log has to keep showing what was actually checked and when.
