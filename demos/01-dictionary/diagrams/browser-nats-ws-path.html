Phase 45 · ARCHITECTURE-ACCOUNTS § connectInfo

Where the browser dials NATS: ws://localhost:9222 → same-origin /nats

connectInfo.wsUrl is NATS_WS_URL returned verbatim — accounts-service never inspects it. It also cannot know the origin the page was served from, so any absolute URL it names is a guess. These two diagrams show the guess failing on a remote deployment, and the path that replaced it.

What actually changed

  • Only the last hop moved. Token minting, TTL, account scoping and the reconnect-on-expiry loop are untouched — the browser still presents the same short-lived, account-scoped JWT, and NATS still authorizes it the same way. nginx forwards the upgrade; it does not authenticate it.
  • The resolution lives in the browser because only the browser knows its own origin. Putting it in Go would mean re-guessing the same thing that was wrong before, just later.
  • nats joined the frontend Docker network so the nginx containers can reach it. The trust-tier invariant is unchanged, and arguably tighter: what must not reach the bus directly is the browser, and it still cannot — it dials nginx, which forwards exactly one path.
  • Host port 9222 stays published, but now only for the nats-ui container (under review), whose own page dials it directly. The demo's three frontends no longer do.
  • Mixed content is the failure that would have outlived a hostname fix. Worth stating plainly, because "point it at the real host" looks like the obvious repair and only solves half of it.
