Temporal in the transporter vetting saga — what it is, and how it is wired here

Transporter vetting is a process that waits — for a human to review each compliance document, and for an external check on the transporter's GIT — goods-in-transit insurance cover — and must survive the service restarting halfway through. Temporal is the durable execution engine that holds that in-flight state. This page covers Temporal's building blocks first, then how they meet NATS JetStream, Postgres and organizations-service in Phase 38.

What the integration forced us to get right

  • One task queue serves every tenant, so activities must resolve their own connection. An activity that captured a NATS connection at construction would publish one tenant's events over another tenant's account. Tenant therefore travels on every workflow input and ProfileActivities calls tenants.Manager.ProfileEvents(tenant) per invocation — BR-TP58. A tenant this service holds no credential for writes nothing rather than falling back.
  • A Schedule has no caller to inherit context from. The goods-in-transit monitor fires months after the vetting attempt that created it, so its Tenant has to be baked into the schedule's own arguments. Leaving it out is exactly how the first live monitor run failed, with "tenant is not connected"; the spec now asserts the schedule action's arguments, not only the workflow input.
  • Retries need the append to be idempotent. Temporal will re-run an activity whose result it never saw. AppendProfileEvent publishes with a stable message ID (<org>:<type>:<attempt>:<step>) so JetStream's duplicate window returns the original PubAck instead of creating a second domain transition.
  • Determinism reaches back into the inputs. The required document references are sorted before the workflow starts: Temporal replays the input, and a set that reordered between runs would be pointless history churn.
  • Resubmission reuses the workflow ID. WORKFLOW_ID_REUSE_POLICY_ALLOW_DUPLICATE plus an empty run ID on the signal means a reviewer's verdict always reaches the live attempt without anyone tracking run IDs — and it is why Submit routes a Rejected profile into Resubmit rather than starting a second workflow.
  • The workflow is the only thing that knows it just reached Vetted, which is why it creates the goods-in-transit monitor schedule itself rather than a projection watching for vetted. Creating a schedule that already exists is treated as success, since a resubmitted attempt vets again under the same identity.

Why not just NATS?

  • JetStream remembers what happened; Temporal remembers what is still owed. Reconstructing "two of three documents approved, insurance check outstanding, waiting" from the event log on every restart is possible but is a bespoke state machine — and Phase 38 already proved the cost of writing such logic twice, when the projector and the aggregate's own Apply() disagreed about a resubmit's status.
  • Timers and retries are the part you don't want to hand-roll. A five-minute recurring goods-in-transit cover check, an activity retry policy, and a compensating branch on failure are one-liners here; on raw NATS they are a scheduler, a dedup table and a dead-letter policy you own forever.
  • The boundary held. Temporal never became a data store: no query in this service reads from it, and if Temporal were removed the transporter profile would still be fully reconstructable from the TRANSPORTER stream alone. That was the design constraint, and it is worth re-checking on any future workflow.
