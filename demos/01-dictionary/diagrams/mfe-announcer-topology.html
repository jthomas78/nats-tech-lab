Where the plugin announcer runs

Phase 13e gave every announced micro-frontend plugin its own announcer sidecar container, so five plugins cost ten containers and a plugin developer ships two runtime units. Phase 14 moves the announcer into the plugin's own process. The connection topology is what decides whether that is safe, so it is drawn here before and after.

What the drawing settles

  • There were never two connections in one place. There were two containers with one link kind each: HTTP-only with zero bus access, and bus-only with no listener. Phase 14 co-locates them without adding or removing either.
  • Per-plugin totals are unchanged. One NATS connection and one HTTP listener, before and after. The lab still opens five announcer connections on five distinct credentials.
  • frontend is not optional and backend is new. The registry's BR-AS61 probe dials the plugin over frontend, and nats lives on backend, so the merged container must join both.
  • The no-proxy rule is what makes that safe. The Go host's route set is exactly the asset root and /healthz, asserted as a set, and the signing seed and credential mount outside the asset root.
  • Withdrawal still needs an explicit SIGTERM. BR-AS54 is untouched, and the new risk the merge introduces is that a failure in the serving half must exit without unregistering.
  • The credential's name is the one open question. The holder process stops being an announcer, and this repo names a dedicated credential exactly for its holder.
