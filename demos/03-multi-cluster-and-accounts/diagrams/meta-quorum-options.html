Who is still alive to take a write?

Demo 02's double-capture page asks where the bytes land. This page asks a different question: when a region goes dark, who can still accept a JetStream management call. Four topologies. Every number below was measured on this machine, not drawn from the docs.

Read this first. A JetStream meta group is every JetStream server in one JetStream system. It holds the list of streams, and it votes. A stream group is the replicas of one stream and always lives inside one cluster. Losing meta quorum does not stop data — it stops change. Measured in this lab: with au stopped, core pub/sub worked, reads worked, and a publish to an existing stream took ODOMETER from 1 to 2 messages. Only nats stream add failed, with JetStream system temporarily unavailable (10008). A WAN cut is a change freeze, not an outage.

C and D are not rivals. C keeps one shared subject space and rescues the quorum. D gives up the shared space and removes the shared quorum. Pick by which you would rather own: less config, or less coupling.

Five config traps, each one measured the hard way

  • Every JetStream cluster member needs at least one route — including the seed. The forming-a-cluster docs page shows a routeless seed because that page does not enable JetStream. With JetStream on, a routeless seed dies: [FTL] Can't start JetStream: JetStream cluster requires configured routes or solicited leafnode for the system account. One route is enough — gossip finds the rest. Duplicate Route in the log is gossip finding a peer twice, and is normal.
  • A one-node arbiter still has a cluster block, so it still needs a route. Point it at itself: routes: [ nats://127.0.0.1:6540 ]. Without it the arbiter is the only server of the seven that fails to start.
  • A one-node hub must have NO cluster block at all. I gave it the self-route trick from the arbiter and it believed in a peer that does not exist — leader=None, cluster_size=2, num_routes=0. Delete the whole block; JetStream then runs standalone and is healthy. (A three-node hub is a normal cluster and is better anyway.)
  • Every region server lists ALL of the hub's leaf ports. This is what made the hub-node failure self-heal — four orphaned links moved to another hub node by themselves. One URL makes one hub node a single point of failure for that server. 
    leafnodes {
  remotes: [
    { urls: [ "nats-leaf://lb:lb@127.0.0.1:7560",
              "nats-leaf://lb:lb@127.0.0.1:7561",
              "nats-leaf://lb:lb@127.0.0.1:7562" ], account: LB }
  ]
}
  • A cross-domain mirror needs the API prefix. Without external.api the mirror looks only in its own domain and sits at 0 messages forever, with no error. 
    { "name": "AU_COPY", "num_replicas": 3,
  "mirror": { "name": "ODO",
              "external": { "api": "$JS.au.API" } } }

The arbiter is not automatically safe

A voting server with JetStream enabled is also a storage server. I measured where data actually lands.

8 x  stream add P1..P8 --replicas 1   (no --cluster, client on za)
  → all 8 landed in cluster za. None on arb.   placement prefers the client's local cluster

stream add ARB1 --replicas 1 --cluster arb
  → SUCCEEDS.  Placement Cluster: arb   Leader: arb-1

stream add ARB3 --replicas 3 --cluster arb
  → no suitable peers for placement (10005)   one node cannot hold R3

client connects DIRECTLY to arb:4540, stream add DIRECT
  → SUCCEEDS.  cluster=arb  leader=arb-1
  • Good news: ordinary traffic will not drift onto the arbiter. Placement follows the client.
  • Bad news: an explicit --cluster arb, or any client that connects straight to the arbiter's client port, creates a real R1 stream there — unreplicated data in your smallest, least protected location.
  • So: keep clients off the arbiter's client port, or fence it with placement rules. Do not assume "it only votes".

What the gateway lab also proved

  • The meta group is not per account. Measured with 3 JetStream accounts live: accounts with JS: 3, meta groups: 1, leader: za-2, size: 6. An account is a wall for data, not a wall for availability — a freeze hits every account at the same moment.
  • Inside one account, a stream name is unique across the whole supercluster. Creating ODOMETER a second time from the far side gives stream name already in use with a different configuration (10058). The nastier half: stream info from the far side then succeeds and hands back a working handle to the other region's stream. It looks local. It is not.
  • Accounts are the only hard wall. The same name ODOMETER in LB_ZA and LB_AU both create cleanly, with different Placement Cluster and independent message counts.
  • Placement decides where bytes sit. It does not separate systems. --cluster za|au is about storage, not about survival.
  • A WAN cut is a change freeze, not an outage. With au stopped: core pub/sub worked, reads worked, and a publish to the existing ODOMETER took it from 1 to 2 messages. Only stream add failed. Restarting au returned the leader and unblocked it.

How to measure this without fooling yourself

  • Never fake a WAN cut with docker network disconnect. Measured 2026-09-09: disconnecting a network from a running container also drops that container's published host ports. Every reading afterwards is a Docker artifact. The first run of that experiment reported "both regions died" and even core NATS pub/sub appeared to fail — impossible from a meta split. Stop the far region's processes instead.
  • Interest across a leaf link needs about 5 seconds to spread. My first cross-region pub/sub test waited 2 seconds, read 0 received, and nearly got written up as a failure. The same test at 5 seconds read 3 of 3.
  • The created timestamp is not proof of identity. Two genuinely different streams in two accounts both reported created 2026-09-10 15:15:15. Use Placement Cluster and message count to tell them apart.
  • Prefix scratch configs so cleanup cannot reach the real lab. A tidy-up pkill -f "nats-server -c za-" matched the user's identically-named files and killed the live lab — twice. Scratch files now carry a t- prefix, so the kill pattern is pkill -f "nats-server -c t-" and cannot match.
  • Read the meta group, not the logs. curl "localhost:8231/jsz?meta=1" gives leader, cluster_size and the peer list with online flags. Quote the ? — zsh globs it. Also useful: /varz, /routez, /gatewayz, /leafz, /accountz, /jsz?accounts=1.

Open, and honest about it

  • Figure D buys isolation with bookkeeping. Nothing replicates by itself. Every cross-region copy is a mirror or source that somebody writes down and maintains. That is a real cost and it is not visible in the diagram's tidy boxes.
  • Not measured: whether source/mirror survives across two gateway-joined clusters with different domains (Figure B's topology). Given placement already fails with 10005 there, I would not trust it without a test.
  • Not measured: the hub as a real JetStream store rather than a pass-through; leaf reconnect behaviour with many regions; mirror catch-up time at production volume.
