NATS Migration Strategy — one Australian cluster to a leafnode hub with two leaves

A revised, six-phase path from a single pilot cluster in Australia to Demo 03’s T5 shape: a control hub in Africa with an Australian leaf and a South African leaf. Every phase has a gate. Cluster = 3 NATS instances throughout.

What changed from the first draft

  • The domain goes in on day one. The original plan converted a live, data-holding Australian cluster to a leaf with a jetstream.domain in phase 3. That restarts every server and changes the estate-wide JetStream API address from $JS.API to $JS.au.API. Set on an empty cluster, it costs nothing. The conversion phase disappears.
  • Moving the hub and adding a region are two phases. The original phase 4 did both at once.
  • Every phase has a gate. A named test must pass before the next phase starts.

The matrix is the only prevention for silent double capture. T5 can store a deliberate copy in two places; the written ownership rule is what makes that copy intentional, per D03-R6. Accounts are the tenant boundary. They are not the domain or the cluster (D03-R2). Cross-account sharing is explicit export/import with subject renaming (D03-R8, variant E).

Gate 0. The matrix is written and signed off. No servers exist yet.

Phase 1

One Australian cluster, built leaf-ready

Domain, cluster name, server names and accounts are set at first boot. Clients are domain-aware from day one, so the API address never changes again.

Gate 1. The pilot runs; streams and KV buckets work; every client is domain-aware.

Phase 2

Add the control hub, join it by leaf link

This is already T5 with one leaf, so the original phase 3 has disappeared. Use a leaf link, not a gateway. Put all three hub URLs on every leaf server; one URL makes one hub node a single point of failure.

Gate 2. (1) Stop the whole hub. AU still elects a leader, stores publishes and creates a new 3-replica stream (D10–D14). (2) Every cross-domain mirror carries external: { api: "$JS.hub.API" }. A missing prefix gives a healthy-looking stream with zero messages and no error (D03-R7); alert on mirror lag, not mirror existence. (3) The subject matrix matches reality. Nothing is stored twice.

Phase 3

Make auth survive the hub being gone

Do this while the hub is still next door and a wrong answer is free. Answer three questions separately: (1) account/JWT lookup: put a resolver copy in AU; (2) auth callout / token issuer: put capacity in AU or AU cannot issue new tokens when the link drops; (3) leaf credentials: decide where they live and who rotates them.

Demo 03 used plain user/password auth in hand-written .conf files. It offers no evidence for operator-mode JWT behaviour. This phase is unmeasured and must be tested, not assumed. Decide and write down whether AU serves cached refdata or refuses when the hub is gone.

Gate 3. Cut the hub link for 30 minutes. AU keeps authenticating, keeps serving refdata, and nothing queues forever.

Phase 4

Move the hub to Africa. The hub only.

1. Build the Africa hub with the same domain and cluster name but new server names; never reuse a name. 2. Copy hub state across: auth and refdata only, so small. 3. Add the three Africa leaf URLs alongside the Australian ones. 4. Verify. 5. Soak for a week. 6. Only then remove the Australian URLs and shut the old hub down.

AU now pays ocean latency to reach auth. Phase 3 is what makes that survivable.

Gate 4. AU runs on the Africa hub for a full week. Repeat the Gate 2 hub-loss test.

Phase 5

Add the South African leaf. Full T5.

ZA points straight at its final hub and never does a URL swap. Every AU↔ZA copy is a mirror written by hand with external.api pointing at the other domain, because nothing copies itself across a leaf link.

Gate 5. Run full T5. Kill the hub and both AU and ZA keep working (D10–D14). Publish to an AU-owned subject and confirm it is stored once, not twice.

Still unmeasured — do not assume these

  • The hub as a real store. Demo 03’s T5 hub only relayed. This plan’s hub holds auth and refdata. If that means JetStream streams on the hub, it is untested here; Demo 03’s own “Still open” list says so.
  • Mirror catch-up at production volume. No lag or bandwidth figure exists in either shape. Measure it in Phase 2.
  • Leaf reconnect with many regions. Only two leaves were ever measured.
  • Operator-mode auth across a leaf link. Demo 03 used plain passwords. Phase 3 is where this is measured for the first time.
