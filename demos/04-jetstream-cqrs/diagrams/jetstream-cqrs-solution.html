JetStream as an event source, with CQRS

The demo answers one question with a number: rehydrating an aggregate, how much does a snapshot buy you?

What the drawing commits us to

  • One stream is the only source of truth. Every command is judged against a Vehicle rehydrated from ODOMETER, not against either KV bucket.
  • The aggregate holds only what a rule reads. Vehicle has no TotalKm; the read model owns the total, trips, and query-facing status.
  • Two buckets, not one, make the split visible. nats kv ls must show odometer-write beside odometer-read, because snapshot and read model are different jobs.
  • LimitsPolicy is load-bearing. The demo deliberately replays from sequence 1, so retention must preserve events after consumers have acknowledged them.
  • The snapshot is an optimisation, never the truth. It may seed rehydration, but the tail always follows because an asynchronous consumer can only be behind the log.
