One Log,
Two Projections,
One Snapshot

Eight patterns measured on one NATS server and one small Go binary. Each card states the mechanism, what it buys, what it costs, and the number the lab actually printed. Two of the cards exist because the lab got it wrong first.

The question every card serves

A truck's odometer lives only in a log. Rehydrating it to check one command — how much does a snapshot buy you, and what happens to the answer when you scale the consumer that folds the log?

The rule that orders the deck

A projection is disposable and the log is not. Everything a projection does — caching, denormalising, snapshotting, folding on many workers — is a trade you make against the log, and every one of those trades is paid for in order.

Sourcing

The log is the only source of truth

The stream holds the facts. Every KV bucket in this demo is a fold of that stream and holds nothing the stream does not. The test is brutal and cheap: delete every bucket and every consumer, restart, and see what comes back.

Decision

Is a KV bucket ever allowed to be the truth? No. It is a cache of a fold. If losing it loses data, the design is wrong, not the bucket.

Mechanism
  • LimitsPolicy, never InterestPolicy. InterestPolicy deletes a message once every consumer has acked it, and the replay then returns nothing — with no error. A stream you cannot replay is not an event source.
  • Measured 2026-09-16: both buckets and both durables deleted, both consumers refolded all 74 135 events from sequence 1. Every KV document came back byte-identical, lastTripAt included, to the nanosecond.
  • That only holds because project() uses the event's own stream timestamp and never the wall clock. A projection that reads the clock cannot be rebuilt — it can only be re-approximated.
What it buys
  • A projection becomes disposable. Change its shape, delete it, refold. No migration.
  • Audit for free. The sequence of transitions is the data, not a side table.
  • Time travel. Fold to sequence N and you have the state as of N.
What it costs
  • The log only grows. Retention is a product decision you now have to make.
  • A rebuild is an outage for that read model unless you fold into a second bucket and swap.
  • Determinism is a constraint on your code for ever — no clocks, no randomness, no lookups against data that also moves.
Verdict

Event-source where history is itself a domain concern. Use plain CRUD where only the current value matters — the deciding question is "does anything need to replay this", not "does it change".

CQRS

Two projections, one log

The write side and the read side fold the same stream into different shapes, in different processes, on different durables. They are not two copies of one thing. They disagree on purpose, and the disagreement is the whole of CQRS.

Decision

Should the write-side snapshot just reuse the read model? No. The aggregate must carry only what a command is judged against. Everything else belongs to the reader.

Mechanism
  • odometer-write holds {state, lastSeq} for the aggregate. It answers one question: may this command be appended?
  • odometer-read holds the denormalised view a screen wants — total kilometres, last trip, plate, status.
  • Measured 2026-09-16: after a full rebuild both sides landed on the same lastSeq for every vehicle, and the same status and plate.
  • They do not agree on totalKm, and must not. The write-side aggregate has no such field: Travelled leaves it unchanged, because no command is ever judged against a distance.
command→ rehydrate aggregate→ check rules→ append to log→ projector folds→ read model
What it buys
  • The write-side snapshot stays tiny for ever. Ten thousand trips move the read model and leave the aggregate byte-for-byte identical. That is why Card 03's number does not decay.
  • Read shapes are free to change. A new screen is a new fold, not a schema change.
  • Write and read scale apart, and fail apart.
What it costs
  • Two folds to keep correct, and two durables to operate.
  • The read model is eventually consistent. A command that succeeds is not yet visible on the screen that triggered it.
  • "Which bucket is right?" becomes a question people ask. The answer is neither — Card 01.
Verdict

Put a field on the aggregate only when a rule reads it. If the field exists to be displayed, it belongs to the read model, and keeping it out is what keeps rehydration cheap.

Performance

What a snapshot buys

Rehydrating from sequence 1 is linear in the length of the log. Rehydrating from a snapshot is one KV get plus the tail, and does not care how long the log is. That is the whole finding, and the shape matters more than the multiple.

Decision

Is a snapshot worth the second moving part? Yes, past a few thousand events — and the reason is the slope, not today's ratio.

Measured · 2026-09-16 · NATS 2.14.3 in Docker on a laptop · 10 001 events on one vehicle · best of three
RehydrationEvents readTimeGrows with the log?
From sequence 1, no snapshot10 00125 msYes, linearly
From the snapshot, then the tail01.1 msNo
  • About 23x here, and it grows. Take the log to 100 000 events and the left figure goes up tenfold while the right one does not move.
  • The snapshot is always stale. The write consumer is asynchronous, so it trails the log. Rehydration reads the snapshot and then replays from lastSeq + 1. Measured mid-catch-up, the same command read 2 900 events of tail in 12 ms.
What it buys
  • A constant-time write path on a log that is not constant.
  • It is cheap to add later — the snapshot is derived, so there is nothing to migrate.
What it costs
  • Code that stops at the snapshot is a bug, not a shortcut. You must always replay the tail.
  • A second consumer to run and watch.
  • Below a few thousand events it buys a millisecond and costs you a component.
Verdict

Snapshot the write side, never trust it alone, and measure the slope rather than quoting a multiple — the multiple is a property of the day you measured it.

Gotcha · method

The ordered consumer that ate the measurement

This demo's headline number was wrong for two days, and it was wrong in the direction that flatters the demo. The replay was not slow because replays are slow. It was slow because the client was creating one consumer per event.

Decision

Which call reads a stream in bulk? Messages(), not Next(). On an ordered consumer, Next() resets the consumer on every call.

Mechanism
  • An ordered consumer is ephemeral and self-healing: the client deletes the server-side consumer and creates a new one whenever it re-positions. Next() re-positions every time it is called.
  • It is visible on the server, because an ordered consumer's name carries a serial number that climbs once per message:
5yL5cUQZHSfSpLY8WvMDXR_32469   delivering stream sequence 32478
  • Before the fix the replay of 10 001 events took 8.2 s. After it, 25 ms. About 99% of the original figure was consumer bookkeeping and about 1% was reading a log.
  • Messages() creates one consumer and pulls batches over it — which is what the client's own documentation on Next() tells you to do.
  • The lesson survived the correction. Replay is linear, a snapshot is constant. What changed is that the number now measures that, and not a mistake in the demo.
How to catch it yourself
  • Watch the server while you measure. nats consumer ls during a replay — a name that changes per message is this bug.
  • Distrust a flattering number. A result that makes your design look good is the one to re-derive first.
  • Sanity-check the rate: 10 000 small events in 8 s is ~1 200/s, which is far below what one NATS server does. The arithmetic was the tell.
Why it is easy to miss
  • No error, no warning. The code is correct, just used against the wrong consumer kind.
  • It gets worse with more data, so it reads exactly like the linear cost you expected to find.
  • A unit test cannot see it. Only the server, or the clock, can.
Verdict

Publish the correction next to the number. A lab whose numbers can only go up is not measuring — the retraction is the part that makes the rest of the deck worth reading.

05
Correctness

A fold is defined by order

A projection is a fold over a sequence. Once you allow a second reader, events can arrive out of sequence, and the fold has to say what it does about that. There are exactly three answers, and the demo makes each one a written rule.

Decision

How does an event compare with the state already folded? Ahead, equal, or behind — and each one has a different, permanent answer.

The comparison, and the three answers · cqrs/domain.go
The event is…RuleWhat the fold doesWhy
Ahead of the folded stateBR-OD06Apply itThis is the normal case.
Equal — seen beforeBR-OD07Ignore it, ack itA redelivery is a duplicate, not new work.
Behind the folded stateBR-OD08Refuse it — ErrOutOfOrderApplying it would move the odometer backwards.
  • BR-OD09 — an undecodable event is permanent. ErrUndecodable is not retried. Redelivering a message the code cannot parse only produces the same failure at ack-wait intervals forever.
  • The rules live in domain.go and nowhere else. No rule enforcement sits in the CLI, the write side, the read side or the HTTP shim — so there is exactly one place to read them and exactly one place to test them.
  • Idempotence is not enough on its own. BR-OD07 makes a repeat harmless. BR-OD08 is the one that stops a late event from corrupting a monotonic value.
What this gives you
  • Out-of-order delivery becomes a named, tested condition, not a mystery.
  • A refusal is visible: it is counted, so a wrong fold shows up as a number.
  • Redelivery costs nothing when the fold is already past the event.
What it does not give you
  • A refused event is lost work, not repaired work. The fold is correct, but incomplete.
  • It only helps a value where order means something. A counter you can add to does not need it.
  • You must carry the compared value (here, the last sequence) in the projection itself.
Verdict

Write the three answers down before you add the second worker. A fold that has not decided what "behind" means has decided it silently.

Scaling

A worker pool buys throughput with correctness

Adding workers to one durable consumer makes the fold faster. It also makes it wrong. Both halves are measured on the same run, on the same log, and neither is a surprise once you see where the order is lost.

Decision

Can you scale a projection by adding workers? Only if the fold is order-free. An odometer is not, so the speed is paid for in dropped events.

Measured · 2026-09-15 · NATS 2.14.3 · ODOMETER_POOL, 10 029 events, three vehicles, -drain
WorkersTimeRateFoldedDropped (out of order)
123.5 s426/s10 0290
212.2 s824/s10 0254
46.3 s1 600/s6 9473 082  (31%)
84.8 s2 100/s4 3385 691  (57%)
  • 3.7x faster at four workers, and a third of the log refused. Those are the same run.
  • One worker drops nothing. One worker cannot race itself, so it is the control row and it proves the fold itself is correct.
  • Where the order is lost: two events for the SAME vehicle land on two workers, and the later one finishes first. The fold then sees an event behind its state and refuses it (BR-OD08).
  • Two dials control how often that happens. The key gap — how far apart two events of one vehicle sit in the log — and the in-flight window, MaxAckPending. The demo seeds three vehicles round-robin, so the gap is small on purpose; at ten vehicles the gap was wide enough that nothing ever raced and the lesson taught nothing.
When a pool is right
  • The fold is commutative — a sum, a set, a last-write-wins cache.
  • Work is partitioned by key, one consumer per key range, so no two workers share a key.
  • You care about drain time more than about per-key ordering.
When it is wrong
  • Any monotonic value — an odometer, a balance, a version.
  • Any state machine with transitions that must not be re-ordered.
  • The loss is silent unless you count it. Nothing errors; the numbers are simply smaller.
Verdict

Partition before you parallelise. If you cannot partition by key, one worker with a correct fold beats eight workers with a fast wrong one.

Tuning

MaxAckPending is the loss dial

The cap on messages in flight for one consumer is usually described as a back-pressure knob. On an order-sensitive fold it is something more direct: it sets how many events can race, and therefore how many get refused.

Decision

What does a low cap do to a large worker pool? It slows the run and protects the fold. It does not idle the workers.

Measured · 2026-09-16 · NATS 2.14.3 · eight workers, 74 109 events, -drain
MaxAckPendingTimeRateWorkers that ackedFoldedDropped
11 m 34.1 s788/s8 of 874 1090
350.0 s1 481/s8 of 857 52916 580  (22.4%)
100033.2 s2 229/s8 of 831 91242 197  (56.9%)
  • Every worker acked at every cap, including a cap of one with eight workers. No worker was starved of work over the run.
  • A single run is not a constant. The cap-3 row re-run gave 54.6 s and 16 722 dropped. The shape holds; the exact figure is a race.
  • A correction to the common wording. The nats.io worker-pool page says a low cap "starves a large set of workers". At an instant that is visible — num_ack_pending 3 with num_waiting 4-5 means four or five workers are holding a pull request and waiting. Over a whole run it is false: the waiting rotates, and all eight do work.
  • Read it as a dial, not a switch. Cap one is serial and correct. A high cap is fast and loses more than half the log.
How to set it
  • Order-free fold: set it high. The cap is then only back pressure.
  • Order-sensitive fold: a cap of one is the only safe value — and it makes the pool pointless, which is the honest signal to partition instead.
  • It is a per-consumer cap, not per worker. Eight workers share one budget.
What it cannot do
  • It cannot make a pool ordered. It only narrows the window in which racing happens.
  • Low caps cost real time: 1 m 34 s against 33 s here, about 2.8x slower.
  • An instantaneous nats consumer info reading will mislead you. Measure over a run.
Verdict

Treat MaxAckPending as the amount of disorder you are buying. Choose it from the fold, not from the throughput target.

Gotcha · delivery

Redelivery after AckWait is not recovery

A worker takes a message and dies without acking. JetStream does the right thing: after AckWait it hands the message to another worker. That is a correct, useful mechanism — and on an order-sensitive fold it arrives too late to be worth anything.

Decision

Does redelivery repair a fold? No. It costs you the whole AckWait and then the fold refuses the event anyway.

Measured · 2026-09-16 · NATS 2.14.3 · four workers, one message abandoned with -kill-at
AckWaitActual waitHanded from → toFold moved on byRedelivered event
30 s30.02 sworker 3 → 4+29 eventsDropped
5 s5.001 sworker 4 → 1+30 eventsDropped
  • The wait IS AckWait, to within 20 ms. There is no extra delay and no early detection. The server cannot know the worker is gone; it can only know the clock ran out.
  • It bought nothing. While the timer ran, the other workers folded about thirty more events past the abandoned one. The redelivery then arrived behind the state and was refused by BR-OD07 / BR-OD08 — exactly as the rules say it must be.
  • A shorter AckWait does not fix this, it only shortens the gap. The redelivered event is still behind by whatever the pool folded in the meantime.
What redelivery IS for
  • An order-free fold, where a late apply is still a correct apply.
  • At-least-once work — sending a message, writing a row keyed by event id.
  • Surviving a worker restart when nothing else is consuming the same key.
What it is not for
  • Repairing a projection that has already moved past the event.
  • Fast failure detection. Its resolution is AckWait and nothing better.
  • Hiding a partitioning problem. The redelivery is a symptom, not a cure.
Verdict

If a lost event must be folded, replay the log from its sequence. Redelivery is a delivery guarantee, and a delivery guarantee is not an ordering guarantee.

Method

Where every number came from

A figure with no date and no machine becomes a constant, and a constant goes stale quietly. Each number in this deck is listed with the day it was taken and the thing it ran on.

The machine
  • NATS 2.14.3, a single server in Docker on a laptop. No cluster, no gateway, no JetStream domain, no operator mode. File storage, LimitsPolicy on every stream.
  • Go client, one process, workers as goroutines over one durable consumer.
  • Streams: ODOMETER (lesson 01), ODOMETER_POOL (lesson 02, its own log so the misbehaving consumer never touches the main stream), ODOMETER_BENCH (the fixture).
