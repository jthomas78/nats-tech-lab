One account, one stream — what a gateway really does to two regions

This page replaces gateway-double-capture-options.html. That page said a gateway lets one publish be stored twice. It is not. Inside one account a stream name is unique across the whole supercluster, so the second region is never allowed to build a second stream. The real problem is quieter and worse: there is only one stream, and you do not choose which region holds it. The recommendation has not changed. The reason has.

What the old page got wrong, and how. Two separate mistakes stacked up.
1. The number came from a bug in our own tool. odometer/main.go held defer sub.Unsubscribe() on a durable pull consumer. Unsubscribing deletes the durable, so every projector run replayed the stream from message 1 and added the same distance again. One region, one account, one message in the stream, no gateway involved:
run 1 -> totalKm=12.5   run 2 -> totalKm=25   run 3 -> totalKm=37.5   run 4 -> totalKm=50
stream ODOMETER   messages = 1   the whole time
2. Even with the bug fixed, there is nothing to capture twice. The second region cannot create its own stream. The overlap and name checks are account-wide and placement-blind, so --cluster au does not help:
za  stream add SHIPPING --subjects 'evt.za.>' --cluster za   created
au  stream add SHIPPING --subjects 'evt.au.>' --cluster au   stream name already in use with a
                                                            different configuration (10058)
So the old Figure A could not be reproduced. It described two streams that JetStream will not let you have. Double capture is real — but in a hub-and-leaf topology, not behind a gateway. See the last section.

What each option actually changes

  • Option 1 changes the subject and the stream name. Same account, same gateway, disjoint filters, distinct names. Cheapest to reason about, most expensive to live with: it spends a design rule we chose on purpose and still leaves two write sides.
  • Option 2 changes the ownership. One writable stream, one write side, a stated one-way copy under its own name. It fixes the drift, not the isolation.
  • Option 3 changes the account. Server-enforced isolation — and it is the only shape that lets both regions keep the same stream name, which means no code changes at all. Then a mirror where a copy is genuinely wanted.
  • The tension to settle first. An account per region cuts across the recorded decision that a tenant is a marketplace-operating business, not a region — and the account boundary is currently the only thing authenticating anything. Deciding option 3 means reopening that.
  • Nothing is decided yet. The probes were purged and the lab is clean.

Where the double capture is real

Not behind a gateway. In a hub-and-leaf topology, where each region is its own JetStream system with its own domain, joined to a hub over leaf links. Measured 2026-09-11 on a nine-server lab — three domains (hub, za, au), three separate meta groups of three:
za  stream add SHIPPING --subjects 'evt.acme.>'   created
au  stream add SHIPPING --subjects 'evt.acme.>'   created   # neither can see the other
one publish in ZA                                za = 1   au = 1   stored twice
The separate domains are exactly why it happens: the overlap check is account-wide, but it cannot reach across a domain boundary, so neither side can refuse. The two regions still shared one account (LB), which is what let the message cross at all. The fix is a fence on the leaf remote, not a domain change:
remotes: [ { urls: [ … ], account: LB,
             deny_exports: [ "evt.>" ], deny_imports: [ "evt.>" ] } ]
After the fence a ZA publish stayed in ZA, ping.> still crossed, and the deliberate mirror on $JS.au.API still followed AU's new event. Full write-up: demos/03-multi-cluster-and-accounts/diagrams/meta-quorum-options.html.

Read the table top to bottom: inside one account, over a gateway, there is no configuration at all that stores a publish twice. The server refuses every one of them. A second copy needs a second namespace — a second account, a second JetStream domain, or a mirror you asked for.

How to measure this without fooling yourself

  • A read proves nothing. A client reaches a stream from either side of a gateway, so "I can read it from au" does not mean au holds it. Read the cluster name: go run . where --region au --account linebooker, or nats stream info SHIPPING -j and look at cluster.name.
  • Never trust a total that only goes up. If a projector run changes the number, check the stream's message count first. Ours did not move. The bug was ours.
  • Do not Unsubscribe or Drain a durable pull consumer. Both delete it on the server, and the durable is the only record of what was already applied. nats consumer ls showing No Consumers defined after a run is the tell.
  • Do not fake a WAN cut with docker network disconnect. It also drops the container's published host ports, so every reading is a Docker artifact. Stop the far region's containers instead: docker stop lab2-au-1 lab2-au-2 lab2-au-3.
  • A gateway cut is a change freeze, not an outage. Each side then sees 3 of 6 peers, below the majority of 4, so neither side can create a stream (10008). Core pub/sub, reads and writes to existing streams keep working.
  • Purge between stages. A leftover stream from stage A makes stage B lie, and the error it lies with is 10058, which reads like a success if you are not looking.
