Trust, Accounts and the Cross-Account Contract

How the messaging system is divided so that one tenant cannot reach another, and what the only permitted path between two accounts is. This sheet shows the mechanism: the trust chain that issues identity, the account plane that isolates, the subject families the platform speaks in, and the export and import grants that let a named subject cross a boundary. Exact subjects, stream settings and permission claims belong to L4.

SCOPE

One question. How does messaging keep tenants apart, and what may cross? Server placement and durable state are on sheet 2.

TRUST

The operator is the only root. It signs account claims; each account signs its own users. A server holds no list of accounts.

ACCOUNT

An account is the isolation boundary. It is not a region, and it is not a business context. Treat it as the tenant wall.

CONTEXT

{context} is the company or business unit and sits in the subject. The tenant sits in the account. The region sits in the deployment.

IMPORT

A tenant reaches shared reference data through an import, then calls it as an ordinary local subject. It never learns the platform subject.

EXPORT

A tenant exports telemetry and read-only stream views. The server rewrites them under a monitor prefix that carries the tenant name.

DENY

No grant means no delivery. Stream create, update, purge and delete are never exported, so a console can read but not damage.

CREDS

One credential per holder, named exactly as the process names itself. A name that does not match in the console is a signal to check.

BROWSER

A browser never holds a credentials file. It gets a short-lived token over a web socket through the web server.

LAB

Proven in the Dictionary POC: four accounts, per-account signing keys, live tenant creation, and the exact grant shape drawn here.

Server Topology, Durable State and Failure Behaviour

Where the messaging servers run, how a site at the edge attaches, what durable state each account holds, how two regions are joined, and what happens when a link breaks. Solid tiles are built and running in the Dictionary POC on a single server. Dashed tiles are proposed for V3 and are not built today. Residency, recovery targets and country rules belong to LB-V3-L3-08; sizing and configuration values belong to L4.

SCOPE

One question. Where do the servers run and what durable state do they hold? Residency and recovery targets are LB-V3-L3-08.

CELL

A cell is one region's runtime. The same shape repeats in each region. A cell is a place, not a tenant.

HA

Three servers is the availability minimum, not a capacity estimate. How big each one is stays open until sizing work is done.

DOMAIN

A JetStream domain marks a cell. It is not a tenancy boundary. The account is the tenancy boundary (sheet 1).

GATEWAY

A gateway joins two clusters. It does not stretch one cluster over a long link. Only listed core subjects cross it.

MIRROR

Durable history crosses a region only as a named mirror or source. There is no cross-region copy by default.

LEAF

A leaf node lets a depot keep working while the link is down, then replay. Nothing like this is built today.

STATE

Streams keep facts. Key-value keeps derived reads. The object store keeps large files. They are not interchangeable.

REPLAY

Streams keep a limits policy so history can be replayed. An interest policy would delete the history instead.

OPEN

Whether two regions get a gateway at all, and which subjects may cross it, is not decided. See the L3-05 register.
