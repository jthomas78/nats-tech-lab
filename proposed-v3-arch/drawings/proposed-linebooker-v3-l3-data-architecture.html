Store Roles, Ownership and the Write Path

Which store owns each kind of data, who is allowed to write it, and how one committed change becomes a published fact, a read model and a warmed cache. Maturity is marked per element: a solid tile is built and running in the Dictionary POC today, a dashed grey tile is a directional V3 position as at 4 September 2026 with no decision of record, and a dashed amber tile needs a named owner. Subjects, streams and grants belong to LB-V3-L3-05; where a store physically sits belongs to LB-V3-L3-08; table, column and migration design belongs to L4.

SCOPE

One question. Which store owns what, and how does one change reach the rest? Reference data and retention are on sheet 2.

MATURITY

Mixed. Solid tiles run in the lab today. Dashed tiles are directional V3 positions as at 2026-09-04.

ROLE

A store is named by its role, never by product alone. The role decides the rules that follow it.

TRUTH

PostgreSQL is the default source of truth. The fact log records what happened; it does not replace the record.

OWNER

One service owns its data. Others are told through a fact or ask through a contract. Nobody else writes.

OUTBOX

An outbox writes the fact in the same transaction as the state, so a published fact can never disagree with the record.

PROJECTOR

One handler writes both the projection and the cache entry. Two writers would let them drift apart silently.

CACHE

The cache is an answer, not a record. A miss falls through to the projection and costs nothing but time.

REPLAY

Event-source only where something must replay the sequence. Current-state-only data stays a plain record.

OPEN

Ten open items sit in the L3-07 register. The outbox and the extraction interface have no V3 ADR.

Reference Data, Distribution and Lifecycle

Where shared values come from, how one changed value reaches every reader without polling, and how long each kind of data is kept. Reference data is more than code lists: it also carries localisation, translation, App Shell theme values and platform configuration. Maturity is marked per element, and every retention period is deliberately shown as not set. This half is directional as at 4 September 2026 and no V3 decision of record exists for retention or lifecycle. Rendering the theme belongs to LB-V3-L3-03; what may be copied to another cell belongs to LB-V3-L3-08.

SCOPE

One question. Where do shared values come from, how does a change spread, and how long is data kept? Stores are on sheet 1.

DIRECTION

Directional. A first pass as at 2026-09-04. Every retention period is deliberately shown as unset.

LAYERS

Three layers answer one lookup. The narrowest layer that has a value wins; the platform layer is the floor.

SCOPED

Every lookup names its context. There is no global unscoped read, so no value leaks between scopes by accident.

MORE

Reference data also carries localisation, translations, theme values and configuration — not just code lists.

THEME

Theme values are stored and served here. Consuming and rendering them in the shell is LB-V3-L3-03.

WATCH

A reader watches the cache. Nothing polls, so a change reaches a screen without a refresh and without a timer.

SHARED

Reference data is the one class that may be copied to every cell. That border rule is set in LB-V3-L3-08.

LINEAGE

The fact log is the lineage record: what changed, when, and in what order. No separate lineage store is proposed.

OPEN

Ten open items sit in the L3-07 register. Retention, tenant exit and the version stamp are the largest.
