Ownership, the Approved List and Trust

The browser application would be one permanent shell that many feature plugins draw inside. This sheet says who owns which part, what the platform's approved list of plugins holds, and what an entry must pass before the shell will count it. Maturity is marked per element: a solid tile is built and running in the Dictionary POC today, a dashed grey tile is a directional V3 position as at 4 September 2026 with no decision of record, and a dashed amber tile needs a named owner. Subjects and grants belong to LB-V3-L3-05; the sign-in token belongs to LB-V3-L3-04; where the files are served belongs to LB-V3-L3-08; field-by-field shapes belong to L4.

SCOPE

One question. How is the browser application composed from a shell and many plugins? Loading and failure are on sheet 2.

MATURITY

Mixed. Solid tiles run in the lab today. Dashed tiles are directional V3 positions as at 2026-09-04.

SHELL

There is exactly one shell. A plugin never starts a second one, and never replaces a global provider.

LIST

A plugin cannot put itself on the list. Only the platform may add an entry, and only an entry may nominate code.

SLOTS

The host screen owns its slots. A plugin fills a slot it is given; it cannot reach into the page and attach itself.

GATES

Three gates, in order, all on the server. Order matters: a good signature over the wrong name must read differently from a bad one.

KEYS

A withdrawn key stops working at the moment of writing, not only at the moment of checking.

LIMIT

A signature covers the description. The code it points at is not signed, so the location list is what bounds it.

RIGHTS

The shell hiding a button is a courtesy. The service refusing the request is the control.

OPEN

Nine open items sit in the L3-03 register. Key ownership and outside publishers have no V3 decision.

Loading, Containment and What a Plugin is Handed

The shell would learn what a plugin is before it runs any of that plugin's code. This sheet reads that rule as five ordered steps, names every state an operator can see, shows what happens when each part fails, and lists what a working plugin is handed. Maturity is marked per element: a solid tile is built and running in the Dictionary POC today, a dashed grey tile is a directional V3 position as at 4 September 2026 with no decision of record, and a dashed amber tile needs a named owner. Where the files are served belongs to LB-V3-L3-08; where labels and theme values are stored belongs to LB-V3-L3-07.

SCOPE

One question. When is a plugin's code fetched, what can break, and what is a working plugin given? Ownership is on sheet 1.

RULE

Description before code. The shell must know what a plugin claims to be before it runs a single line of it.

LAZY

Menus and links are live at step 3. Declaring a link does not download the feature behind it.

ONCE

A plugin starts once per version. A second visit to its screen reuses what is already running.

STATES

Refused and broken are different. One means we would not take it; the other means we tried and it failed.

BLAST

Containment is structural, not a nicer error message. A failed start is rolled back, not left half done.

SLOT

The host names the slot, its shape, its order and how many fit. The plugin fills it and nothing else.

SPLIT

Language belongs to the person; content belongs to the connection. That split is what lets language stay shell-wide.

L3-07

Labels, translations and theme values are stored by the data view. This sheet only shows them being used.

OPEN

The connection broker, the supported version window and mid-session disabling all need a named owner.
