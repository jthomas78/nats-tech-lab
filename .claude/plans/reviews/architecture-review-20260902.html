Architecture review · 2026-09-02

Extensible Application Shell + Micro-Frontend Plugins

Deepening opportunities in lab-shell/src/shell/ and mfe-registry-service. The twelve findings from the previous review are fixed and shipped; these are the seams that read as friction after those fixes, with weight given to the files that moved most in the last few commits.

The pattern that already worked

readPolicy.js pulled every rule about what a registry read means out of bootShell.js into one pure function, leaving the caller to do nothing but apply the decision. Twenty-three specs now run with no shell boot. Three of the five candidates below are the same move, at a different seam — which is itself the signal: the shell keeps growing modules that decide and do in one breath.

Candidate 01

The read-coalescing machine now exists twice

Strong
Files
  • shell/registry/changeSubscription.js — the catalogue's machine
  • shell/registry/healthPlane.js — createHealthPlane, lines ~110-150
Problem

Both modules solve the identical problem: a hint subject fires, a read must follow, only one read may be in flight, a hint landing mid-read must be answered exactly once, and a reconnect gap must force a fresh read. The catalogue's copy was consolidated last week into a single machine with outstanding, chain, pendingHint and reconnects. The health plane still carries the earlier, weaker shape: inFlight plus a boolean pending, with the follow-up read fired from inside the .then() of the read it follows.

They have already drifted. The catalogue's machine compares the hinted revision against what came back and skips a redundant read; the health plane cannot, because a reading has no revision. The catalogue serialises with a promise chain; health re-enters refresh() recursively. One of these has specs for reconnect-during-boot; the other has none.

Under "one adapter is a hypothetical seam, two is a real one", this crossed the line the day the health plane was written. The seam is real now.

Solution

Extract the machine as a deep module — provisionally the hinted reader — with a four-method interface: refresh({unconditional, reason}), start(), stop(), onReconnect(). It accepts the read function and the notify subject; it knows nothing about revisions, catalogues or health. The revision-skip becomes an optional isRedundant(result, hint) predicate the catalogue supplies and health omits.

changeSubscription.js becomes the catalogue's thin binding of that module; createHealthPlane keeps only what is genuinely its own — ageing readings, out-of-order asOf rejection, and the readings map.

Benefits
  • Locality. "How often does the shell read, and when?" becomes one file. Today a fix to burst behaviour has to be found and made twice, and last week's fix was made once.
  • Leverage. The tenant and operator surfaces due to migrate onto this shell will each want the same behaviour; today each would hand-roll a third copy.
  • Tests. The four hard specs — reconnect before start, one read at a time, hint behind a queue, nothing after stop — are written once against a fake read, and both callers inherit them. The health plane currently has no equivalent spec at all.

Candidate 02

contributionRegistry.index() decides and does in one pass

Strong
Files
  • shell/contributions/contributionRegistry.js (376 lines, one function of ~100)
  • shell/extensions/extensionPoints.js, shell/auth/permissions.js (its inputs)
Problem

index() holds the whole placement ruleset — permission refusal, route-prefix first-claim-wins, capacity, suspension when a slot's owner is withdrawn, the available/disabled verdict, cross-plugin sort, and the unresolved-nav sweep — and it applies all of it directly into seven reactive containers while mutating PluginStatusRecords it was handed.

The consequences are visible in the file. restore() has to call this.index([plugin]) re-entrantly and delete from indexedPluginIds first to get past the guard at the top — placement rules can only be re-run by faking a first visit. dropFrom() exists solely because the containers must be spliced in place. And a spec for "does a shell-footer aimed at a full region still leave the route placed?" must construct extension points, a permissions object, a status map and a plugin array, then read a getter.

Apply the deletion test to the reactive containers: delete them and the rules remain, intact and unstated. That is the shape of a decision trapped inside a store.

Solution

Same move as readPolicy.js. A pure decidePlacements(plugins, {permissions, capacityOf, occupancy, withdrawn}) returns a plain placement plan: {placed, refusals, suspended, statuses, prefixOwners}. index() shrinks to applying that plan to its containers and forwarding the status verdicts.

restore() then re-decides honestly — it asks the policy for a fresh plan for one plugin against current occupancy — instead of deleting a bookkeeping entry to trick the guard.

Benefits
  • Leverage. The interface a caller learns drops from "seven reactive collections and an incremental, non-idempotent index" to "give me a plan".
  • Locality. Every placement rule is in one file. Today "why did this contribution not appear?" is answered by reading a hundred-line loop with five interleaved concerns.
  • Tests. Placement specs stop booting Vue reactivity entirely. Withdrawal and return — the hardest cases, BR-AS56/AS58/AS59 — become plan comparisons rather than before/after reads of a mutated store.

Candidate 03

The loader writes restoreTo straight into the status record

Strong
Files
  • shell/loader/pluginLoader.js:55 — record.restoreTo = FAILED
  • shell/loader/pluginLoader.js:152 — record.restoreTo = ACTIVE
  • shell/registry/pluginStatus.js — the machine that owns the field
Problem

PluginStatusRecord is careful, well-documented, and explicit that an illegal transition throws rather than being swallowed. Its interface is transition / withdraw / restore — and restoreTo is its private memory of where a withdrawal came from.

The loader reaches past that interface and assigns the field twice, because it has a case the machine has no word for: an import or an activate() that lands after the plugin was withdrawn. transition() throws on a withdrawn record by design, so the loader routes around it.

The rule this encodes is real and subtle — a plugin withdrawn mid-load must come back active so activate() is not called twice (BR-AS59), or failed if the load lost. But it is enforced nowhere. Nothing stops a third caller writing restoreTo = 'loading', which would resurrect a plugin into a state with no in-flight load behind it.

Solution

Give the machine the word it is missing. One method — provisionally settleWhileWithdrawn(status) — that accepts only a status a withdrawn plugin may legally return to, throws on anything else, and is a no-op if the record is not withdrawn. The two loader lines become calls; restoreTo goes back to being private.

This is a small change with a disproportionate effect on the interface: after it, the whole truth about plugin status lives behind three methods on one class, and pluginStatus.spec.js becomes the complete statement of the state machine.

Benefits
  • Locality. The withdrawal-mid-load rule moves next to every other status rule, instead of living as two bare assignments in the loader.
  • Leverage. Callers learn one closed vocabulary. No field on the record is writable from outside.
  • Tests. The rule becomes assertable without a loader, a federated adapter or a timing race — today it can only be reached by racing a withdrawal against an import.

Candidate 04

The chrome's attention rules are spread across a template

Worth exploring
Files
  • src/App.vue — statusOf, healthOf, isActive, and the dot markup
  • shell/registry/statusRollup.js, shell/registry/healthText.js
Problem

BR-AS60's precedence rule — a failure dot beats a health dot, never both — is written as an early return inside healthOf() in App.vue, and then re-stated in the template as a v-if/v-else-if pair that must stay in the same order to remain true. The rollup for the topbar pill is already extracted (statusRollup.js) precisely because "two surfaces need it"; the per-item mark has the same property and was not.

There is no third surface yet, so this is a smaller claim than 01–03. It becomes real the moment the Plugins screen or a migrated app wants the same mark.

Solution

A pure navMark(pluginId, {statuses, health}) returning {tone, title} | null, with the precedence inside it. The template renders one conditional dot instead of two ordered ones.

Benefits
  • Locality. One rule, one place, instead of a function and a template ordering that must agree.
  • Tests. BR-AS60 becomes a table-driven spec instead of a mounted-component assertion about which span rendered.
Candidate 05

The operator projection is assembled in the transport adapter

Speculative
Files
  • registry/internal/browserrpc/endpoints.go — EntryView, curate()
  • registry/internal/application/service.go — Curated, Sources
Problem

curate() joins three sources — the stored document, the registration sources map, and a drift snapshot — and decides two rules while doing it: an unknown source is spelled out rather than left blank, and a nil drift reader yields awaiting-check. Those are contract decisions sitting in a JSON adapter. A second transport for the same operator view (a REST admin surface, say) would have to restate them.

Marked speculative deliberately: there is exactly one transport today, so by "one adapter is a hypothetical seam" this does not yet qualify. It is listed so the decision is conscious rather than accidental if a second one arrives.

Solution

Move the join into the application layer as a CuratedView the service returns whole; browserrpc keeps only JSON tags.

Benefits
  • Tests. The unknown-source and unchecked-drift rules become application-layer Ginkgo specs rather than assertions about a marshalled reply.
  • Locality only pays off with a second transport. Until then this is a wash.

Top recommendation

Start with 01 — the hinted reader.

It is the only candidate where the seam is proven rather than argued: two modules already implement the same machine, and they have already diverged — last week's consolidation of burst and reconnect behaviour landed in the catalogue's copy and not the health plane's. That is not a risk, it is a bug waiting for someone to notice that a health hint arriving during a read behaves differently from a catalogue hint arriving during a read.

It is also the cheapest. The catalogue's machine is 119 lines, freshly written, and already has the four specs that would become the shared suite; the health plane's copy is smaller and has none. The refactor is mostly deletion, and the deletion test comes back the right way — remove the extracted module and the same coalescing logic reappears in two places.

Then 03 (an afternoon, and it closes an unenforced rule), then 02 — which is the largest and the one most worth grilling properly, since the placement plan's shape is a real design decision and not a mechanical extraction.
