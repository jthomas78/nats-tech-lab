How reference data flows from commands through JetStream into two competing read-model shapes, and how the browser stays live via KV Watch → SSE.

Shape A

KV as read model

Events project directly into NATS KV. The KV bucket is the read model — no Postgres read table. KV revision = entry version. Reads never touch Postgres.

Shape B

KV as cache in front of Postgres

Events project to Postgres first (source of truth), then refresh the KV cache. Cache miss falls through to Postgres and backfills KV. Evict any row to watch the miss path.

Data Flow

Write Path

Every state change is a command that produces a JetStream event. The HTTP caller gets 202 Accepted immediately — projections are async.

  1. 1
    POST /api/entries or PUT /api/entries/{ctx}/{type}/{id} hits the REST handler.
    rest/handlers.go → decodes JSON body, calls command handler
  2. 2
    Command handler validates the DictionaryEntry, wraps it in an EntryEvent{OccurredAt}, marshals to JSON, and publishes to JetStream subject DICTIONARY.entry.created or DICTIONARY.entry.updated.
    commands/commands.go → internal/jstream/stream.go (LimitsPolicy, FileStorage)
  3. 3
    REST handler returns 202 Accepted with the entry payload. The client does not wait for projections.
  4. 4
    JetStream delivers the event concurrently to two durable consumers: dict-shape-a (Shape A handler) and dict-shape-b (Shape B handler). Each acks explicitly; projection failure → nak → redeliver.
    eventhandler/handler.go

Shape A — KV as Read Model

Projection

  1. 1
    Shape A event handler receives the event from JetStream consumer dict-shape-a.
  2. 2
    Deserializes EntryEvent, preserves original CreatedAt on updates, writes entry JSON to KV bucket dict-a-{context} under key {entityType}.{id}.
    KVStore.Put() — internal/kvstore/kv.go; bucket created lazily on first write
  3. 3
    Acks the JetStream message. The KV revision number becomes the entry version.

Read Path

  1. 1
    GET /api/shape-a/entries/{ctx} or /{ctx}/{type}/{id}
  2. 2
    Query handler calls KVStore.Get() on dict-a-{context}. No Postgres involved.
    application/queries/get_entry.go — ShapeAQueries
  3. 3
    Response includes "source": "kv" and the KV revision as version.

Shape B — KV as Cache in Front of Postgres

Projection

  1. 1
    Shape B event handler receives the event from JetStream consumer dict-shape-b.
  2. 2
    Upserts to Postgres first: INSERT ... ON CONFLICT DO UPDATE. On conflict, increments version and sets updated_at. Returns the persisted row (with server-assigned version and created_at).
    postgres/repository.go — Upsert()
  3. 3
    Writes the persisted entry (canonical version from Postgres) to KV cache bucket dict-b-{context} under key {entityType}.{id}.
    KVStore.Put() — bucket created lazily
  4. 4
    Acks the JetStream message. Projection failure at either step → nak → redeliver.

Read Path — Cache Hit

  1. 1
    GET /api/shape-b/entries/{ctx}/{type}/{id}
  2. 2
    Query handler calls KVStore.Get() on dict-b-{context}. Entry found → return immediately.
    application/queries/get_entry.go — ShapeBQueries.GetEntry()
  3. 3
    Response: "source": "kv-cache", "cacheHit": true.

Read Path — Cache Miss + Backfill

  1. 1
    KV Get returns nats.ErrKeyNotFound (entry evicted or bucket empty).
  2. 2
    Falls through to PostgresRepo.Find(). Returns ErrNotFound if truly absent.
  3. 3
    Backfills KV: writes retrieved row into dict-b-{context} so next read is a hit.
    demo: DELETE /api/shape-b/cache/{ctx}/{type}/{id} → evicts a key → next GET shows miss path
  4. 4
    Response: "source": "postgres", "cacheHit": false.

Rehydration via LimitsPolicy Replay

The DICTIONARY stream uses LimitsPolicy retention — events are kept after acknowledgement (unlike InterestPolicy which deletes on ack). This means a consumer can start from sequence 1 and replay the full history at any time.

  1. 1
    Delete or wipe a KV bucket (e.g. nats kv purge dict-a-en-GB).
  2. 2
    Restart the backend (or trigger a consumer reset). The event handler replays from stream sequence 1.
  3. 3
    The KV bucket is rebuilt from events — no data loss, no manual re-seeding.
    internal/jstream/stream.go — RetentionPolicy: nats.LimitsPolicy

This is also why InterestPolicy was rejected: consumers would have to be live at publish time or events would be dropped on the floor, making replay impossible.

Reactive Updates — KV Watch → SSE → Pinia

  1. 1
    Browser opens GET /api/watch/{context} (EventSource). The SSE handler starts a KV Watch on both dict-a-{ctx} and dict-b-{ctx} buckets concurrently.
    rest/sse.go — SSEHandler
  2. 2
    The watcher replays current state first (all existing keys → nil marker → then live). Each KV update emits an SSE event: {"shape":"a"|"b", "key":"currency.GBP", "op":"PUT"|"DEL"|"PURGE", "revision":N, "value":{...}}.
  3. 3
    The Vue frontend's EventSource listener routes events to the correct Pinia store (Shape A or Shape B). The store mutates reactively — no polling.
    Pinia stores here are the frontend analogue of server-side materialized views: both are projected read models derived from an event stream, one layer further out.
  4. 4
    A 15-second heartbeat (:ping) keeps the SSE connection alive through proxies and load balancers.

API Reference

Method Path Description
POST /api/entries Create entry → publishes entry.created → 202
PUT /api/entries/{ctx}/{type}/{id} Update entry → publishes entry.updated → 202
GET /api/shape-a/entries/{ctx} List all Shape A entries for context (reads from KV)
GET /api/shape-a/entries/{ctx}/{type}/{id} Get single Shape A entry (KV only, source: "kv")
GET /api/shape-b/entries/{ctx} List all Shape B entries (reads from Postgres, canonical)
GET /api/shape-b/entries/{ctx}/{type}/{id} Get Shape B entry — KV hit or miss → Postgres → backfill
DEL /api/shape-b/cache/{ctx}/{type}/{id} Evict a KV cache key (forces miss on next GET)
GET /api/watch/{ctx} SSE stream — KV Watch on both buckets, live + replay
GET /healthz Health check
