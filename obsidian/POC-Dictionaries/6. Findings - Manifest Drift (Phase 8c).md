# Manifest drift — observation without curation

The registry and a deployed plugin each hold a manifest, for different reasons.
The registry records what an operator approved; the plugin describes what was
deployed. A redeploy can change the second without changing the first. Phase 8c
makes that disagreement visible without letting a plugin change its own grant.

The registry checks preloaded entries in the background. Admin shows agreement,
named differing fields, or **not checked**. A failed fetch is not evidence that
the two copies agree, even if an earlier fetch succeeded. Neither drift nor an
outage disables the entry or replaces its curated content.

The deployment boundary mattered: browser `localhost` names the user's machine,
while the same address inside the registry container names the registry itself.
A separate startup map translates existing allowed browser origins to container
addresses. It never extends the allowlist; missing mappings remain not checked.

Checks use bounded GETs, refuse redirects, retry once and run on their own
schedule. NATS readers use the last observation without waiting for HTTP. The
integration specification deliberately holds an origin open while Admin and
shell reads complete, then proves that observing drift changes no stored entry,
revision, audit history or notification.

The limitation is explicit: this is a last observation, not a live attestation.
It is lost on service restart, invalidated by a curated edit, and refreshed by
the next background pass. It checks manifest content, not the JavaScript code
served at the remote URL. The operator still decides what to curate.
