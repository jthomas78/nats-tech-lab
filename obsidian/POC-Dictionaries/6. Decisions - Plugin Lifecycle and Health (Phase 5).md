# Plugin lifecycle and health — approved decisions, not implementation findings

On 2026-08-31 the user settled 14 design questions and approved updating the Phase 5 plan, rules
and required test cases. Implementation has not started. These decisions extend the independently
deployed plugin model described in [[6. Findings - Manifest Drift (Phase 8c)]].

Stopping a service should make its health visible without taking an already loaded feature away.
Withdrawal instead follows an explicit action: operator disable or signed publisher unregister for
a dynamic plugin. Static plugins retain reload-based behavior. Publisher withdrawal preserves
approval, but a publisher cannot reverse an operator disable or revoked trust by returning.

An occupied withdrawn route stays in place with an explanation. The shell removes contributions,
not the JavaScript module, and an unchanged authorized return restores cached contributions without
activating twice. Changed definitions require reload. A slot disappearing suspends only placements
into it; contributing plugins can keep working elsewhere. No claim is made that callbacks stop or
that unmounted form state survives.

Frontend and backend health answer different questions, so they will be shown separately for both
classes. The registry checks frontend `/healthz` through explicitly mapped allowlisted origins and
backend readiness over narrowly scoped NATS request/reply. Deployment config chooses backend targets;
an absent mapping means not configured, while an empty list deliberately means frontend-only.

The accepted timing is a check every five seconds, a two-second timeout, two failures before
unavailable and one success to recover. Fifteen seconds without fresh observations becomes
unknown/stale, with last-check time visible. A working frontend health endpoint cannot guarantee
that a user's browser can load every JavaScript asset.

The distinction from manifest drift is deliberate: drift compares deployed declarations against
curated content; health observes availability; neither changes approval or removes content. Health
will cover both lifecycle classes independently of source. Explicit lifecycle replaces inference,
and legacy unclassified entries will be backfilled as static to preserve their existing behavior.

The plan and BR-AS52–65 test matrix specify the required failure cases, including replay ordering,
operator-disable races, withdrawal during loading, slot restoration and stale snapshots. Those are
planned tests, not evidence of shipped behavior. Runtime findings belong in a later implementation
update after the specs and UI checks have actually run.

## Implementation update (2026-09-01)

Phase 5a–5e is built. Registry Ginkgo 358/358 with nothing skipped, `shared/natsready` 6/6,
lab-shell Vitest 480/480, Admin Vitest 335/335, clean builds.

Three findings worth keeping.

**Ageing at read time, not on a timer.** A stale reading has to stop claiming to be current, and the
obvious way to do that is a background sweep. Doing it in the read instead — `Snapshot(now)` in Go,
`signalsFor(id)` in the browser — removed a whole class of problem: nothing wakes up, nothing leaks,
and the answer is right at the moment it is asked for. The browser also restates the fifteen-second
window itself, so a registry cannot make a browser trust a reading for longer than the platform
decided.

**A hint should be rare or it teaches shells to ignore it.** The health checker compares the SERVED
snapshot, not the raw probes, before it hints. Two failures that have not crossed the threshold are
the same news as none. Hinting every five seconds would have been correct and useless.

**Presence is not readiness, and this bit in practice.** A service holds its NATS connection open
while its database is gone, so a responder that answers because it is subscribed says nothing. Every
ask runs the real check with a deadline and caches nothing.

**Still to run:** the live 1920×1080 walkthrough — stop a service, watch the signal move, restart,
watch it recover, lose telemetry, watch it go stale. No unit spec observes that. The NATS grant
changed, so the stack needs `docker compose down -v && docker compose up --build` first.
