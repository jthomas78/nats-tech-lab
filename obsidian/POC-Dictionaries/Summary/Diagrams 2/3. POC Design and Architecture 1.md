
## Shape at a glance

Two independent Go services, one NATS server, one Postgres instance shared by convention (not by code):

![Dictionary system architecture](dictionary-system-zoom.png)

- **Shipping Backend** (`:18080`) — the original event-sourced Ship + Container domain (Shapes A/B/C).
- **`refdata-service`** (`:18081`) — the dictionary/reference-data service this POC set out to answer. Plain Postgres CRUD, no aggregate, no event log — "nothing in the platform ever needs to replay a dictionary item's history to reconstruct it."
- The two are connected by exactly one integration point: `internal/refdataconsumer` in the shipping backend reads refdata-service's mirrored KV cache directly. **There is no Go dependency between the services** — only a shared convention on bucket naming and JSON shape.

Where this sits relative to the legacy Shape A/B/C naming: `refdata-service` is architecturally closest to **Shape B generalized platform-wide** — "the same write-through-cache pattern generalized from 'cache for one demo's read model' to 'platform-wide reference data distribution.'" If you've internalized Shape B, you already understand most of this service's shape.

## KV Stores and Streams

### KV buckets

| Bucket | Owner | Contents | Written by | Read by |
|---|---|---|---|---|
| `dict-a-{context}` | Shipping Backend | Shape A ship read model | Shape A event handler | SSE watch |
| `dict-b-{context}` | Shipping Backend | Shape B write-through cache of the Postgres ship projection | Shape B event handler | Shape B queries (KV→Postgres fallback), SSE watch |
| `container-{context}` | Shipping Backend | Container terminal/manifest read model, key `container.{ISO6346}` | container projector | terminal queries, SSE watch |
| `meta-{context}` | Shipping Backend | cross-cutting lookup sets (currently just `known-containers`) | meta projector | meta queries, SSE watch |
| `refdata-{context}` | **`refdata-service`** | per-item cache entries (`{typeKey}.{code}`) + a `{typeKey}._meta` version/count/timestamp record | `refdata-service`'s cache projector (write-through on every mutation, backfilled on a REST read-path miss) | shipping backend's `refdataconsumer`, refdata-service's own REST reads, SSE watch |

The `refdata-{context}` bucket is the one genuinely cross-service relationship: **written only by `refdata-service`**, **mirror-read only by the shipping backend** — never the other way around.

### Streams

| Stream | Owner | Subjects | Retention | Role |
|---|---|---|---|---|
| `SHIPPING` | Shipping Backend | `emea.events.acme.ship.>`, `emea.events.acme.container.>` | `LimitsPolicy`, unbounded | The actual event store — ship/container command events, replayed for Shape C and hydration |
| `REFDATA` | `refdata-service` | `emea.refdata.acme.*.changed` | `LimitsPolicy` + **48h `MaxAge`** | A bounded **notification/pointer feed** — deliberately *not* a source of truth. Nothing in-repo currently consumes it as a stream; the shipping backend reads the mirrored KV bucket directly instead |

The retention contrast between the two streams is the clearest artifact of the "NATS carries distribution, not the dictionary's event store" constraint from [[2. Requirements and Constraints]] — one is genuinely unbounded because it *is* the system of record, the other is capped at 48 hours because it explicitly isn't.

## Postgres

One Postgres **instance**, two isolated **schemas** — the shipping backend has no access at all to `refdata.*`, and vice versa. This is a real boundary, not just a naming convention (compare to the KV bucket, where isolation is convention-only — see [[4. Outstanding POC Tasks]]).

**`public` schema (shipping)**:

| Table | Purpose |
|---|---|
| `ships` | Shape B canonical ship projection |
| `containers` | container projection, surrogate UUID primary key, natural ISO-6346 key unique |
| `ports` | plain reference data — not event-sourced, seeded per fleet context |

**`refdata` schema (reference data)**:

| Table | Purpose |
|---|---|
| `dictionary_types` | type registry — key, name, description, category |
| `dictionary_items` | the actual lookup values, keyed by `(context, type_key, code)` |
| `dictionary_localizations` | per-locale label/description, cascades on item delete |
| `dictionary_references` | typed edges between items (e.g. "country → default currency") |
| `dictionary_locales` | which locales exist per context, and which is default |
| `dictionary_set_versions` | the Q5 versioned-read source of truth — one version counter per `(context, type_key)` |

Note that `ports` is a useful counter-example worth knowing about: it used to be hardcoded (`BASE_PORTS` in a Vue component) and became Postgres-backed master data — but it migrated into the **shipping backend's own** table, not into `refdata-service`. That was a deliberate "no" — see [[4. Outstanding POC Tasks]] for why.

### The `refdata` schema, column by column

Full entity-relationship diagram, including which deletes cascade and which don't:

![Dictionary database ER diagram](dictionary-er-diagram.png)

A few schema decisions worth calling out explicitly in a presentation:

- **No surrogate key on `dictionary_items`.** It's keyed on the natural composite `(context, type_key, code)` — unlike `Container` in the shipping domain, reference data has no external interchange standard forcing a surrogate key.
- **No per-item version column.** `dictionary_items` originally had one; it's been dropped. Versioning is a property of the *type's whole set*, not the row — tracked in `dictionary_set_versions` and stamped onto the KV cache entry on every mutation (BR-D04). This is the same set-level versioning referenced in [[2. Requirements and Constraints]] — it's a staleness counter, not a version history.
- **Delete cascades are asymmetric on purpose.** Deleting an item cascades to its localizations and to references where it's the `from` side — but **not** where it's the `to` side. An item can't be hard-deleted while something still references it (BR-D02), and that's enforced in the domain layer, not by the foreign key itself.
- **`dictionary_locales` and `dictionary_set_versions` have no formal FK relationship** to the other tables — they're standalone, per-`(context, type)` or per-`context` tables, not part of the item/localization/reference graph.

## API accessibility

Both services expose REST + Swagger + SSE. **Updated Phase 15d:** live-update transport is no longer uniformly SSE — `frontend/seafreight-app` (Sea Freight Flow) now holds a single **NATS WebSocket** connection and uses `api.*` request/reply plus `notify.*` subscriptions instead of REST + SSE, which is what removed the ~5-SSE-streams-per-tab browser connection-limit problem. `frontend/admin` and `frontend/refdata` remain on REST + SSE.

**`refdata-service`** — the dictionary-as-a-service surface:

```
GET    /api/refdata/{context}/types
POST   /api/refdata/admin/types
GET    /api/refdata/{context}/{type}                    (?all=, ?locale=)
GET    /api/refdata/{context}/{type}/{code}              (?locale=, ?expand=)
GET    /api/refdata/{context}/{type}/{code}/localizations
GET    /api/refdata/{context}/{type}/{code}/references
GET    /api/refdata/{context}/{type}/completeness        (?locale=)
GET    /api/refdata/{context}/{type}/cache-status
POST   /api/refdata/admin/items
POST   /api/refdata/admin/items/{type}/{context}/{code}/deprecate
POST   /api/refdata/admin/items/{type}/{context}/{code}/reactivate
PATCH  /api/refdata/admin/items/{type}/{context}/{code}/attrs
DELETE /api/refdata/admin/items/{type}/{context}/{code}
POST   /api/refdata/admin/references
GET    /api/refdata/{context}/locales
POST   /api/refdata/admin/locales
POST   /api/refdata/admin/localizations
GET    /api/refdata-watch/{context}         (SSE)
```

`GET .../{type}/{code}` does a **best-effort cache backfill on every read** — this is the server side of the Q5 miss-repair path.

**Shipping backend** — the consuming/demo side:

```
GET    /api/refdata-demo/{context}/{type}/{code}   → {"source": "kv-cache" | "api-refetch"}
GET    /api/refdata/types/{type}
GET    /api/refdata/locales
GET    /api/refdata-watch                            (SSE, fixed context acme — Phase 16d)
GET    /api/kv/buckets                               — new: lists every KV bucket with live status
GET    /api/kv/buckets/{bucket}/watch                 (SSE) — new: full replay + live PUT/DEL/PURGE feed
```

The `/api/kv/buckets*` pair is new — it's what backs the **KV Inspector** panel in the Admin/NATS Debug frontend: a bucket browser grouped by prefix family, with row-level JSON preview and a capped live "recent updates" feed (only one bucket's SSE connection open at a time, to stay under the browser's per-origin connection limit).

The three-path framing is a clean way to describe how any consumer actually gets a value, worth reusing verbatim in a presentation:

1. **Postgres directly** — ground truth, bypasses the cache entirely
2. **REST** — cache-first internally, backfills the KV cache on a miss
3. **NATS KV directly** — a consumer embedded in another service (the shipping backend's pattern), zero network call on a cache hit

And one explicit *non*-path, worth calling out because it's counter-intuitive: the `REFDATA` JetStream stream is **not a retrieval path** — it carries only a change pointer and "cannot answer 'what is this item's value' by itself."

The full lifecycle end to end — a normal cache hit, the REST fallback on a miss/stale entry, and what happens after a mutation — is laid out message-by-message here:

![Shipping UI dictionary read sequence](dictionary-runtime-sequence.png)

The live-refresh path (bottom section) is worth narrating explicitly, since it isn't obvious from the KV/REST split alone: a mutation lands on `refdata-service`, its projector writes the KV entry *and* publishes a pointer on the `REFDATA` stream — but the **SSE watch that actually refreshes the UI is doing its own direct `kv.Watch()` on the KV bucket, not consuming that stream**. The pointer publish and the live-refresh trigger are two independent mechanisms that happen to fire from the same mutation, not one causing the other.

### How consumed is this, really?

Worth being precise about scope here, because it's easy to overstate: **today's Shape A/B/C reconstruction queries don't depend on refdata at all.** Neither `application/queries/` nor `internal/eventhandler/` in the shipping backend references refdata-service in any way. The *only* place the backend actually exercises `internal/refdataconsumer` is a standalone demo route, `GET /api/refdata-demo/{context}/{type}/{code}` — it proves the KV-first/REST-fallback pattern works, but it is not wired into the real read side. If a future feature needs a reference-data label while reconstructing a response, this is the pattern it would use — it just isn't in use for that purpose yet.

## Verified, not just designed

Worth saying explicitly in a team presentation: this was proven live against the real stack, not just designed. A hazard-class lookup was verified to return `source: "kv-cache"` on a hit; version-mismatch detection was proven with a test that manually desynchronizes an entry's stamped version from `_meta` to force the fallback path. The build also caught a real bug along the way — a nil-interface gotcha (`domain.ChangeNotifier` receiving a typed-nil `*kvcache.Projector`) that would have silently *not* been nil and panicked when NATS was unavailable in tests. That's exactly the kind of thing a POC like this is supposed to surface before it reaches production code.
