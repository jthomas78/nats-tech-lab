# 4. Outstanding POC Tasks

These are named gaps — things the POC deliberately did not build, with a stated reason — not oversights. Presenting them this way to the team matters: each one is a scoping decision, not an unknown unknown.

## Multi-tenancy

**Status: a string convention today, not enforced isolation.** Both services hardcode their tenant/region as constants for this lab:

```go
const Region = "emea"
const Tenant = "acme"
```

(present verbatim in both `refdata-service/refdata/internal/kvcache/kvcache.go` and the shipping backend's `dictionary/internal/domain/events.go`, each with a comment acknowledging it's a lab shortcut, not multi-tenant).

Worth flagging to the team: the shipping backend's "context" (fleet-scoped: `global`, `atlantic-fleet`, `pacific-fleet`) and refdata-service's "context" (tenant/region-scoped: `emea-acme`) are **two different context spaces that happen to share a field name** — the code calls this out explicitly where the two meet. Don't assume "context" means the same thing across both services when reading code.

There's also no NATS-level access control separating the two services today — "refdata-service owns this bucket" is a codebase convention enforced by nobody importing the wrong package, not an enforced permission boundary. Real tenant isolation (separate NATS Accounts, per Requirement in [[2. Requirements and Constraints]]) is scoped as its own future spike, not yet started, checklist items unchecked.

## Configuration Data

**Status: reserved, not built.** The type-category model (see [[5. Data Types]]) already has a `config` category slot — but it has **zero types registered under it today**. It's explicitly marked "reserved for later" everywhere it appears (BR-D09, the architecture doc's metadata-projection table, the Phase 11.7 category table). The architecture doc even names the intended future namespaces — `tenant.*` (tenant-specific configuration), `locale.*` — both marked **"future,"** not "in progress."

If/when this gets picked up, it slots into the same type-category mechanism already built — this isn't a redesign, it's populating a slot that was left open on purpose.

## UI Theming Data

**Status: a placeholder spike, not yet a formal requirement.** This is the newest and least-settled item — raised as a question ("does it make sense to put theme data in the dictionary service?") on 2026-07-17, explicitly scoped as "not a formal requirement yet."

The interesting part for a team discussion: theming was explicitly argued to be **architecturally different** from every other reference-data type this POC handles, not just "another `ui-copy`-style type." The reasoning: a full-page flash of the *wrong tenant's brand colors* before a client-side fetch resolves is far more visible and jarring than a mismatched text label ever is. Every other refdata type in this POC uses the same pattern — client fetches, KV-first with REST fallback, renders once resolved. Theme data's proposal is different on purpose: **server-side or edge injection** (nginx, a small Go handler, or an SSR shell) so the correct theme is present before first paint, not fetched-and-swapped after.

First checklist item on this spike, verbatim: **"Confirm this is still wanted as a real requirement before scoping further."** That's a genuinely open question for the team, not a rhetorical one — worth actually asking in the round-2 discussion.

## Smaller named gaps (worth a mention, not a section)

- **AI-assisted translation drafting** — the review-gate business rule (BR-D07) is built and tested, but the actual drafting endpoint/UI is parked, not started.
- **Snapshotting** — not implemented on the shipping backend's write side. Named as "the main scalability gap: as the stream grows, every write gets slower" — relevant to any capacity conversation, since it's on the event-sourced side, not the refdata side.
- **`ship-status` isn't consumed back yet** — it's seeded into refdata-service as a `domain-enum` type (see [[5. Data Types]]), but the shipping backend doesn't read it back through `refdataconsumer`. Today it exists for lookup/localization purposes only, not as the backend's runtime source for status codes.
- **NATS `micro` request-reply spike** — optional, parked alongside the AI-translation work.
