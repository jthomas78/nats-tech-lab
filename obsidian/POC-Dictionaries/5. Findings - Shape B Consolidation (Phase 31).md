Findings write-up for Phase 31 — Consolidate to Shape B: Retire Shapes A and C. Implementation detail lives in the repo (`ARCHITECTURE.md` § "Shape Classification — Variant Identifiers", `ARCHITECTURE-ADMIN.md` § 4.8, `BUSINESS_RULES-SHIPPING.md` BR-019/BR-020/BR-024/BR-038); this note is the stakeholder-facing *why Shape B won* and *what we learned closing the comparison out*.

## Summary

The POC's founding question was which CQRS read-model shape to build the shipping domain's Ship/Container aggregates on, so three were built side by side and measured: **Shape A** (NATS KV directly as the read model, no Postgres), **Shape B** (Postgres canonical projection + an eager write-through KV cache), and **Shape C** (event-sourced reconstruction — current state rebuilt by replaying the full JetStream log on every read, no KV, no Postgres). That question is answered: **Shape B won**, and the other two have been retired from the codebase rather than left running as dead weight. `queries.ShapeA`/`queries.ShapeB`/`queries.ShapeC` collapsed into one `queries.Ships`; the `dict-a`/`dict-b` KV buckets collapsed into one `ships` bucket; the Admin UI's three-panel comparison collapsed into one panel. All ~120 backend specs and both frontend test suites stayed green throughout the consolidation.

## Why Shape B won

Each shape had a real, measured weakness the comparison was built to surface:

- **Shape A (KV as the read model) had no fallback on a miss.** Nothing backed the KV bucket — if an entry was evicted, corrupted, or simply never written (a redelivered event that lands after a bucket reset, say), the read model was permanently wrong for that key until the projector happened to see another event for it. Fast on a hit, but "fast and sometimes silently missing data" is a worse trade than it sounds like for anything a browser bootstraps a fleet view from.
- **Shape C (event-sourced reconstruction) degraded with stream depth, measurably.** Phase 10's baseline #1 (`perf/scenarios/shape-c-reconstruction.js`, since removed) measured `GET /api/shape-c/fleet` at p50 0.90ms / 100 events, 5.71ms / 1,000 events, 44.64ms / 10,000 events — roughly linear, ~10× depth → ~8× latency. Correct forever, but not something you can serve an interactive read from once a fleet's history grows past a few thousand events without a snapshotting mitigation (the reason Phase 104 exists at all).
- **Shape B paid a real cost too — Postgres is a network hop on a cache miss — but it's the only one of the three with no permanent-miss failure mode and no unbounded-latency failure mode.** A miss falls through to Postgres and backfills the cache; the cost is one extra round-trip, not a wrong answer or a growing one. That's why it's the shape the demo now runs on exclusively.

## The trap: this was not a pure deletion

Shape A looked like it existed purely for the demo's side-by-side comparison panel, but it quietly owned two things Sea Freight Flow (the Port Management frontend) actually depended on in production:

1. **`publishNotify`/`publishRawNotify` for `entity="ship"` fired *only* from Shape A's projector.** Shape B's projector explicitly did not publish — the two shapes agreed, at the time, that publishing twice per event would be a duplicate, so only one of them did it. Deleting Shape A first would have silently killed Sea Freight Flow's live fleet updates: no error, just ship rows that stop updating.
2. **`queries.ShapeA.ListShips` (reading the KV bucket directly) backed `api.*.shipping.ship.list.v1`** — Sea Freight Flow's bootstrap/reconnect query. Deleting Shape A first would have left that endpoint with nothing behind it.

The fix was sequencing, not caution alone: sub-phase 31.1 moved both responsibilities into Shape B's projector *first* and confirmed the full test suite was green — only once Shape A was verifiably unused in production did 31.2 delete its code. The resulting rule is now stated directly rather than left implicit: BR-024's invariant is "exactly one publisher per event," not "Shape A publishes, Shape B doesn't."

One consequence worth naming plainly: the ship-list query used to be a KV read (Shape A) and is now a Postgres read (Shape B, BR-038) — a real latency-characteristic change, not just a rename. The KV cache is a per-entity cache and is never enumerated for a list, on principle: a list built from KV would return whatever subset happened to be cached, which is a correctness bug wearing a performance optimization's clothes.

## Honest caveat found while retiring the isolation-proving test

The existing tenant-isolation test (`tenant_switch_test.go`) used to prove "tenant A's ships are unreachable from tenant B" by calling Shape C's fleet-reconstruction endpoint, which reads only the currently-connected NATS account's own JetStream stream — genuinely account-isolated by construction, same as Shape A's KV-only reads. Rewriting that test after Shape C's removal surfaced something neither retired shape's isolation test had ever had to confront: **Shape B's Postgres fallthrough is not NATS-account-isolated** — the `ships` table is a single shared Postgres instance, scoped only by the `{context}` business-unit string, with no NATS-account column at all. Two different tenants that happened to use the same context string could, in principle, read each other's ship data via the Postgres fallthrough path, even though the NATS account boundary would correctly stop them from reaching each other's KV or JetStream data directly. This was always true of Shape B — it just was never exercised by the isolation test until Shape C (the test's actual account-scoped assertion mechanism) was removed. Filed as a follow-up investigation, not fixed here: it's a design decision (schema change or explicit scoping), not a one-line patch, and Phase 31's job was consolidating shapes, not re-architecting Postgres tenancy.

## Stakeholder summary

- Shape B won because it has no permanent-miss and no unbounded-latency failure mode, not because the other two were badly built — both were correct, working implementations of real event-sourcing patterns, retired only once the comparison had a confirmed answer.
- Retiring the "losing" shapes was not a pure code deletion: Shape A quietly backed two live production paths, and the plan explicitly sequenced migrating them before deleting anything, verified green at each step.
- The comparison surfaced one real, previously-untested gap on the winning shape — Postgres isn't NATS-account-isolated the way KV and JetStream are — which is now a tracked follow-up rather than a silent risk.
- Everything the three-shape comparison was built to prove is preserved here and in the code's own history (`Main-POC-Plan-ARCHIVE.md`, git log) even though the losing shapes' code is gone — the POC's actual deliverable was always the answer, not the losing implementations.
