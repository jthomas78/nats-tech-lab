Findings write-up for Phase 28 — Distributed Tracing for Inter-Service Comms. Implementation detail lives in the repo (`ARCHITECTURE-COMMUNICATIONS.md` § 2.1, `ARCHITECTURE-ADMIN.md` § 4.5, `BUSINESS_RULES-SHIPPING.md` BR-036/BR-037); this note is the stakeholder-facing *why* — specifically the two questions the plan flagged as needing a findings note: correlation id vs. trace id, and why the trace store is Shape A.

## Summary

Phase 28 replaced a message-log-shaped observability side-channel (`obs.rpc.*`/`obs.api.*`, paired request/reply events keyed by NATS's own reply-to inbox) with a real distributed trace (`obs.trace.*`, one W3C-style `traceId` per logical request, propagated explicitly through every hop). The two ideas — correlation id and trace id — look interchangeable at a glance (both are "an id that groups related messages") but solve different problems, and conflating them is exactly what made the old mechanism unable to answer "what did this request cause." The new trace store that assembles the result is itself an application of this lab's own Shape A pattern (KV as read model, no Postgres tier) to its own telemetry — not a new fourth shape, and not an oversight that Postgres was left out.

## Correlation id vs. trace id

**Correlation id (`correlationId` on `traceSpan`) is a NATS-native, single-hop concept: the reply-to inbox subject (`req.Reply()`) a requestor mints fresh for one request and the responder publishes its answer back to.** It exists only where a synchronous NATS request/reply actually happens, and a new one is minted for every hop — a browser call into shipping-service that triggers a further call into refdata-service produces *two* correlation ids, one per hop, with nothing on the wire linking them. The old `obs.rpc.*`/`obs.api.*` mechanism used exactly this as its grouping key, which is why a two-hop call showed up in the Request/Reply panel as two unrelated rows, and why anything with no reply-to at all — a JetStream event, a `notify.*` push, a KV write triggered by a projection — produced no correlation id and therefore no record whatsoever. A timed-out call with no responder was the worst case: zero correlation id ever existed for it, so it emitted nothing at either end.

**Trace id (`traceId`) is an application-level concept that has to survive exactly the boundaries correlation id can't cross.** It is minted once, at the true origin of a causal chain (the browser, or a root NATS call with no inbound `traceparent`), and carried forward explicitly — as a W3C `traceparent` header — through every subsequent hop, service, NATS account boundary, and async leg, including the ones with no reply-to subject at all (an `evt.*` JetStream publish carries `Traceparent` via `PublishWithTrace`; a `StartFromHeaders` span on the consuming end reads it back off the message). Because propagation is explicit rather than piggybacked on a wire mechanism that only exists for synchronous replies, a `traceId` can and does span a REST entry point, a command handler, an async projector, and a cross-account `rpc.*` hop, all landing in the same trace.

The practical fix wasn't "replace correlation id with trace id" — `traceSpan` (BR-036) keeps `correlationId` as a genuine superset field, unrenamed, because it still answers its original narrow question (which specific reply matched which specific request, at the wire level) and older `obs.rpc.*`/`obs.api.*` consumers still decode it. What changed is that **causal-chain stitching is no longer correlation id's job.** `traceId`/`spanId`/`parentSpanId` do that instead, and they're designed to keep working exactly where correlation id structurally can't: async, fan-out, and cross-account.

## Why the trace store is Shape A

The trace store (`TRACES` JetStream stream + `trace-request-reply` KV bucket, one durable merge-consumer building a per-`traceId` KV entry from the span stream) is this lab's own Shape A — JetStream event handler projecting directly into KV, reads served straight off KV, no Postgres read table — applied to its own telemetry rather than to Ship/Container. That's a deliberate fit, not the default reached for out of convenience:

- **Nothing ever needs to replay trace history from scratch as a domain concern.** Shape C (event-sourced reconstruction) exists in this lab specifically for cases where a consumer must rebuild state by replaying a log — the trace store has exactly one consumer (the merge-projector) and it runs forward once, deduping by `spanId` on redelivery, never rebuilding a trace from a clean replay of the whole stream. That's the same "does anything need to replay this" test `ARCHITECTURE.md`'s Ship/Container-vs-ports-registry discussion already established for this codebase, applied a second time to a very different kind of data.
- **Only current per-trace state matters, and only for a short, bounded window.** A trace is diagnostic — useful while debugging a request that just happened, not a durable business record. The `TRACES` stream is deliberately short-lived (`LimitsPolicy`, 1-hour `MaxAge`, 64 MiB cap) — the same shape as the `RPCTRACE` side-channel it replaced, not the unbounded retention `SHIPPING` gets. Shape B's whole reason to exist — a canonical Postgres projection behind an eager-writethrough KV cache — is to give a read model durability and queryability beyond what KV alone offers. Trace data doesn't want that: it doesn't need to survive a KV bucket eviction, doesn't need SQL-shaped historical queries, and every payload on a span is already redacted and size-capped before it's published (BR-036) specifically so it stays cheap and short-lived to keep around. Adding a Postgres tier under it wouldn't buy durability this data is designed not to want — it would just add a second, longer-lived retention surface for the same (already-redacted, still potentially sensitive) request/response bodies the 1-hour cap deliberately bounds.
- **KV alone already gives the Admin UI everything the panel needs**: a bootstrap fetch of the bucket's current entries plus a live `notify._platform.kv.trace-request-reply.>` watch for new spans arriving — `TraceWaterfall.vue`'s exact read pattern, with no REST endpoint added for it (`BR-036`'s Phase 28g amendment). That's Shape A's read path, unchanged from how the shipping domain's own Shape A KV buckets are read.

The interesting twist versus Ship/Container's Shape A is that the trace store *does* keep its source stream around, briefly, rather than treating it as pure write-once-then-discard input — the 1-hour retention exists so the merge-consumer can dedup redeliveries and, in principle, rebuild after a restart, which a truly disposable event would not need. It's still Shape A (JetStream feed → KV projection → KV reads), just with a retention window sized to the merge-consumer's own operational needs rather than to Ship/Container's replay-for-audit needs.

## Stakeholder summary

- Correlation id and trace id are not two names for the same thing: correlation id is NATS's own reply-matching mechanism, scoped to one hop; trace id is this phase's own explicit propagation mechanism, scoped to a whole causal chain, and it's the only one of the two that can cross an async or cross-account boundary. The old observability side-channel broke specifically because it only had the first.
- The trace store is Shape A on purpose — the same "replayable log in JetStream, current state in KV, Postgres deliberately absent" pattern this lab already validated for reference data (`refdata-service`, [[3. Findings - Dictionary Service (Phase 11)]]) and for Ship/Container, now proven a second time on a structurally different kind of data (short-lived diagnostic telemetry vs. long-lived business state) — reinforcing that the shape choice tracks "does this need Postgres's durability/queryability," not "is this JetStream-backed data."
