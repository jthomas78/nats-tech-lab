## Why this needed its own investigation

The original problem statement for this lab framed it at the platform level, not the feature level:

> "For the V3 greenfield logistics platform, we need to evaluate the role of NATS.io in the target architecture, especially in relation to CQRS, event sourcing/event streaming, and materialized views in the form of dictionary/reference data or stores."

The trigger was a genuinely open architectural question — **what is the correct responsibility split between JetStream (event backbone), NATS KV (fast lookup/cache/watch), and Postgres (transactional source of truth)** — and reference data was picked as the concrete thing to build against, because it's small enough to build end-to-end but forces a real decision on that split.

## "Dictionary" is an overloaded word — that was the first problem

Before any design work happened, the investigation had to disambiguate what "dictionary" even meant, because it could plausibly refer to any of:

- UI dropdown / enum values
- Application-level enums (state-machine codes)
- i18n translation strings
- Locale-specific data (country, currency, region, tax, carrier-zone)
- Tenant-specific configuration
- CQRS read-model lookup data

That ambiguity turned out to matter architecturally, not just semantically — different items in that list have different answers to "does this need to be event-sourced." See [[5. Data Types]] for how that eventually got resolved into a concrete "type category" model, and [[2. Requirements and Constraints]] for the decision heuristic itself.

## The core architectural question

Stated plainly: should dictionaries live **directly in NATS KV** (fast, but no durable system of record), **in Postgres with KV as a distribution cache** (durable, with a cache-coherence problem to solve), or **be event-sourced and projected into KV via handlers** (full history, more machinery than reference data usually needs)?

The investigation was deliberately framed as comparing shapes rather than committing to one upfront — this is the same "Shape A vs. Shape B" comparison the shipping domain uses for its own CQRS read models, generalized to the question of where *reference* data specifically should sit.

A hard requirement threaded through all of this: "data is derived from the event source, and must be returned based on application context (such as tenant, region, or locale), ensuring that lookups resolve to the correct values for the current execution environment" — i.e. whatever shape wins, it has to be context-scoped from day one, not bolted on later.

## What "done" looked like

The investigation explicitly wanted more than a design document — it wanted "a demoable application... so the approach can be showcased and the implementation reviewed in code." That's why this POC has working Go services and Vue frontends behind it, not just an architecture note.

## Where this landed

Quoting the retrospective finding directly, because it's the cleanest statement of the outcome:

> "The dictionary/reference-data question from the original problem statement is answered by a working, tested implementation... The core architectural question — 'does reference data belong as a service with its own KV-distributed cache, and is that worth building over an off-the-shelf product' — has a confirmed **yes** and **build**, with working code and live-verified tests to back both answers, not just a design document."

That service is `refdata-service` — see [[3. POC Design and Architecture]] for what it actually is.
