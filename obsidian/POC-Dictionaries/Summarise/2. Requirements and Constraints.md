## Requirements and Constraints

Concrete rules the POC had to satisfy, and — where it matters — why. These came out of research spikes and real implementation snags, not upfront guesses, so several are stated as decisions with rationale rather than plain requirements.

## Multi-tenancy subject pattern

Every NATS subject in this platform follows an **identifier-first** pattern:

```
{tenant}.{region}.{bounded_context}.{event}
```

This was a deliberate choice against the alternative (namespace-first, e.g. `orders.customer.created`), which is better suited to single-tenant/service-oriented systems. The tradeoff was made explicit at the time:

> "multiple application tenants can share one NATS Account with subject-prefix permissions, but this is soft isolation. For hard tenant isolation, model each tenant as a separate NATS Account and give shared platform services cross-tenant access through explicit imports/exports or separate service credentials."

This POC currently implements the **soft-isolation** side of that tradeoff only — see [[4. Outstanding POC Tasks]] for what hard isolation would take.

## NATS KV key format

Hit during implementation, not anticipated up front: NATS KV keys only allow `[-/_=.a-zA-Z0-9]`. The original design assumed a `{entityType}:{id}` key format; `:` is illegal, so every KV key in this codebase uses `.` as the separator instead (`ship.{shipID}`, `container.{ISO6346}`, `{typeKey}.{code}`, `{typeKey}._meta`).

## Event sourcing vs. plain CRUD — the decision heuristic

This is the single most-reused piece of framing in the whole POC, and it's what ultimately kept `refdata-service` out of the event-sourced world:

> "The deciding question is 'does anything need to replay this to reconstruct state,' not 'does it change over time.'"

Two triggers for revisiting a CRUD choice later:

- The entity gains a **real state machine**
- Someone needs a **temporal query** ("what was in effect on date X")

And an explicit caution against using "is it reference data" as the whole test — some reference-looking tables secretly need history (a rate table where effective-dates matter), and some lifecycle-looking entities are simple enough for CRUD if nothing ever replays them. `refdata-service`'s items satisfy the CRUD side of this cleanly: "nothing in the platform ever needs to replay a dictionary item's history to reconstruct it — only its *current* value is ever consulted."

## Locale / i18n handling

- **BR-D03 — label resolution fallback chain**: requested locale → language → default locale → the code itself. Resolution never fails outright for an existing item.
- **BR-D20 — locale codes must be lower-case.** Not BCP-47-conventional (which upper-cases region subtags) — specifically so locale-code equality is always a plain string comparison, with no canonicalization step needed anywhere it's compared.

## The versioned-cache consistency protocol ("Q5")

Postgres stays authoritative. Every mutation atomically bumps a per-`{context, type}` **set version** (not a per-item version). KV cache entries are stamped with the version that was current when they were written, so any consumer can detect staleness by comparing its cached entry's version against the type's current `_meta` version.

The known limitation is stated plainly, not glossed over:

> "there's a small window between 'Postgres commit' and 'KV cache entry updated' where a reader could see stale state... The version protocol is what makes that window *detectable* by a consumer instead of silently wrong; it doesn't eliminate the window itself."

Shorthand worth reusing when explaining this to the team: **"push for freshness, version for truth."**

## NATS's role is constrained on purpose ("Q6")

> "NATS carries *distribution and notification*; **Postgres stays the source of truth and JetStream never becomes the dictionary's event store**."

This is why the `REFDATA` JetStream stream is bounded (`MaxAge` set) and carries only change-notification pointers — see [[3. POC Design and Architecture]] for the concrete stream config.

## Build vs. buy

Evaluated and explicitly rejected: adopting a commercial reference/master-data-management product instead of building `refdata-service`.

> "Conclusion: build, don't buy — for this platform, at this stage," because commercial RDM/MDM products "solve a **governance problem**... that this platform doesn't have yet," and none provide "this investigation's actual question: a **NATS-KV distribution/cache-coherence layer**."
