# 5. Data Types

## The governance model behind this

Every dictionary type is tagged with a **category**, and the category is what actually answers "compiled into a Go binary, or dictionary-as-a-service?" — it's not an ad hoc judgment call per type.

| Category | Examples | Source of truth | Who edits | Codes at runtime |
|---|---|---|---|---|
| `standards` | currency, country, incoterm, uom, hazard-class | external standards (ISO, Incoterms, UNECE, UN) | data stewards | rarely change; adding one is safe |
| `domain-enum` | ship-status | **the backend domain** (`ShipStatus` Go constants) | devs own the codes; stewards translate | ⚠️ adding/removing a code is meaningless unless the domain actually emits it |
| `ui-copy` / `i18n` | ui-copy | the frontend | translators | keys owned by devs; only labels are translatable |
| `config` *(future, reserved)* | — | — | — | — see [[4. Outstanding POC Tasks]] |

The functionally load-bearing line, stated directly in the design notes: **"UI copy is not reference data at all, and must be namespaced so its keys never leak into business/reference-data queries."** The standards-vs-domain-enum split matters too, but it's more informational — mainly so a steward doesn't invent a `ship-status` code the shipping backend will never emit.

Worth flagging the explicit anti-pattern warning that came with this table: a `category` field plus grouped navigation is the right amount of structure; **a full relational category entity with its own CRUD would be premature** — resist the temptation to formalize this further than it currently is.

One more precision worth stating in a presentation: **`category` is orthogonal to `context`.** Context (e.g. `emea-acme`) scopes *which tenant/region's data set* you're looking at; category classifies *what kind of type* it is, independent of tenant. Don't conflate the two when explaining this to the team.

## What's actually seeded today

`refdata-service` seeds a demo-sized, idempotent subset of standards data at startup (`refdata/seed.go`) — concrete numbers worth having on hand:

| Type key | Category | Description | Item count |
|---|---|---|---|
| `currency` | standards | ISO 4217 currency codes (subset) | 35 |
| `country` | standards | ISO 3166-1 alpha-2 country codes (subset) | 52 |
| `incoterm` | standards | Incoterms 2020 delivery terms (complete) | 11 |
| `uom` | standards | UNECE Recommendation 20 unit codes (subset) | 12 |
| `hazard-class` | standards | UN dangerous goods hazard classes (complete) | 9 |
| `ship-status` | domain-enum | AIS navigational status (mirrors backend `ShipStatus`) | 5 |
| `ui-copy` | ui-copy | Port UI chrome, actions, feedback, accessibility copy | see `uiCopySeed` |

Two locales are seeded per context: `en` (the default — `ResolveLabel`'s fallback landing point) and `es` (seeded purely so the locale switcher and completeness tooling in `frontend-dict` have a second populated locale to exercise). No other locale is seeded — further translations are added at runtime through the Dictionary UI, not by the seed script.

**A subtlety worth getting right when explaining the schema:** every seeded item gets an `Attrs["name"]` (English, on the `DictionaryItem` row itself) *and* proper `en`/`es` rows in `dictionary_localizations`. Only the localization rows are what the actual locale-resolution path (`ResolveLabel`, BR-D03) reads — `Attrs` is a set-level display convenience for the raw item, not the localization mechanism itself. Don't assume `Attrs["name"]` is what a locale-aware caller sees.

## Compiled-in data: the concrete example

`ShipStatus` is the clearest "compiled into the binary" case in this codebase. It's a Go `const` enum in the shipping backend's domain layer (`in-transit`, `docked`, `at-anchor`, `not-under-command`, `restricted-manoeuvrability`) — it drives real state-machine behavior (Ship arrive/depart commands), so the *values themselves* have to stay in Go.

But it's **also** seeded into `refdata-service` as a `domain-enum`-category type, with the seed comment explaining exactly why the duplication is deliberate rather than sloppy:

> "mirrors `backend/dictionary/internal/domain/ship.go`'s `ShipStatus` constants by value — this module has no dependency on the shipping backend's code, so the codes are duplicated here as plain strings rather than imported."

The split this produces: the **codes** stay compiled into the shipping backend (they gate behavior); the **localized labels** for those codes are dictionary data, resolved via the shared frontend composable (`useRefdataLabels.js`) with a hardcoded English fallback map for offline resilience. This is a **value-mirror, not a code dependency** — the shipping backend's `ShipStatus` Go constants and refdata-service's `DictionaryItem{TypeKey: "ship-status"}` rows have no import relationship between them at all, only an agreement that the code strings match.

## Dictionary-as-a-service data: the other three shapes

- **UI copy** — the inverse of the ShipStatus case: copy strings were moved to `refdata-service` as their canonical source (a whole `ui-copy`-category type, described as "the sole authored catalog for Port UI copy"), and a **generated** JS bundle is what's hardcoded now — purely as an offline fallback, machine-generated from the refdata seed file rather than hand-maintained. Authoring direction is the opposite of the ShipStatus case.
- **Ports** — a real "hardcoded → data-driven" migration, but one that deliberately did **not** go to `refdata-service`. Ports used to be a hardcoded `BASE_PORTS` array in a Vue component; they're now Postgres-backed master data, but in the **shipping backend's own** table. Useful precedent for "this needed to stop being hardcoded" without assuming the answer is always "therefore it belongs in refdata-service" — see [[4. Outstanding POC Tasks]] for the latency/failure-mode reasoning behind that choice.
- **Standards data with no hardcoded twin** — currency, country, incoterm, UOM, and hazard-class were seeded directly as refdata-native `standards`/`domain-enum` data with no Go-side hardcoded equivalent ever existing. These were designed refdata-native from the start, unlike `ShipStatus`.

## The pattern to take into the team discussion

There isn't a single migration checklist of "things to move to refdata-service" anywhere in the codebase — and that's arguably correct, not a gap. The `category` field is what actually makes the compiled-in-vs-service-data call, on a type-by-type basis, based on **who owns the value's meaning** (a state machine the domain enforces vs. an external standard vs. frontend copy) rather than a one-time migration exercise.
