Module Federation: from browser mechanics to this lab shell

A visual path from “another build provides a module” to the exact admission, loading, activation, readiness, and mounting boundaries used by demo-catalog.

Keep the two questions separate. Federation answers how a host obtains a public module from another build. The shell answers whether metadata is admitted, where a contribution may appear, when it should load, what API it receives, and what failure state the UI should show.

This visual companion condenses MODULE-FEDERATION-TUTORIAL.md. Online links teach the general mechanism; local links show the implementation actually used here.

01

Plain-language mental model

general MF theoryverified in this repo

A host learns where a separately built remote lives. Its remote entry exposes a container; the container makes named public modules available. The federation runtime registers that location, resolves an exposure, and coordinates a share scope for libraries such as Vue. The export is ordinary JavaScript — the host decides whether to render it as a Vue component.

Host and remote are roles. A general federated app can be both. In this lab, lab_shell consumes and plugins expose.
Exposure is public. ./src/plugin.js is a remote implementation path; ./plugin is the public key the host requests.
Not a sandbox. Catching a rejected load or render error is resilience, not isolation from same-page JavaScript.
02

What happens in the browser

general MF theorybrowser & Vite behaviorruntime request sequence inference

Loading an exposure is asynchronous. Discovery and registration decide where to look; the browser then loads the entry and any required assets, federation coordinates sharing, and the module evaluates before the shell receives its exports. The exact asset/chunk request order is a runtime-and-build implementation detail, not a stable protocol.

03

The local stack and its sharing contract

The Vite plugin shapes each independent build. The runtime performs the late registration and module request in the page. Vue renders returned component definitions. This is deliberately not one responsibility called “federation.”

verified in this repo resolve.dedupe in Vite is a related local build/test precaution; it is not the browser share scope. Likewise, compatible federation libraries do not prove the application-level shellApiVersion is compatible.

04

Three easily confused artifacts

general MF theoryverified in this repo

All three may be JSON-or-JavaScript-looking files near a remote. They do not have the same owner or job. The app-level manifest decides admission and placement; it happens before the direct remote entry is fetched.

05

Exact demo-catalog walkthrough

verified in this reporuntime request sequence inference

Default registry mode discovers curated manifests over the shell’s NATS API. A changed notification is a reread hint, not the registry itself. Only after validation, contribution indexing, and a lazy route or extension request does the shell cross into federation. build mode is an alternate discovery source feeding the same admission and loading path.

Admission first. bootShell.js validates manifests, adds allowed remote URLs, declares extension points, and indexes contributions without importing remote code.
Lazy first use. Lazy routes from shellRoutes.js ask the loader; the adapter normalizes ./plugin to plugin and requests demo_catalog/plugin.
Activation, then mounting. plugin.js exports catalog, intro, and activate. demoGate.js checks readiness after loading but before mount.
06

Responsibility boundaries

verified in this repogeneral MF theory

The useful seam is not “everything about plugins.” Each layer has one question. That separation is why the shell can index features without downloading them, and why loader policy can be tested with an injected adapter.

07

Failure and debugging guide

verified in this repobrowser & Vite behavior

Debug in the order a feature becomes available. Earlier failures mean later layers have no useful evidence yet: there is no value inspecting a chunk request for a manifest rejected before federation was called, or blaming federation for a backend which is unavailable only after code loaded.

  1. Find the plugin in the inventory. Check source mode, discovery success, validation status, and the reason code before investigating browser requests.
  2. Check placement and policy. Confirm the admitted route/component name and allowlisted remote URL; a non-admitted URL should not reach the adapter.
  3. Inspect the browser boundary. Confirm container name, entry URL, public expose, CORS, ESM handling, entry/chunk responses, then distinguish a load deadline from activation.
  4. Only after code loads, check presentation and service state. Separate CSS delivery from the shared styling store, and separate a successful module load from a failed pre-mount demo readiness check.
