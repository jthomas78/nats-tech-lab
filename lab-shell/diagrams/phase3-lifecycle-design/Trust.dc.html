App Shell · Phase 3 design

Three trust gates

Independent, and they compose. Dynamic + signed + operator-enabled is a defensible auto-injection story; dynamic + unsigned is refused outright.
Gate 1
Origin allowlist
Where code may come from. Config-level, server-side. NewAllowlist(nil) permits nothing — the safe default is a shell with no remotes, not a shell with all of them.
A refusal renders as stage and cause only. Never the URL, host, port or credential. BR-AS04, BR-AS20
→
Gate 2
Publisher signature
Who vouched for this manifest. NKey (Ed25519), verified in the domain layer at curation time, against a trusted-publishers table carrying the same revision, audit and disable-never-delete semantics as the registry itself.
Required on dynamic entries only. Operator-placed entries may be unsigned — a human already vouched, and a hello-world plugin should not need an nsc key.
→
Gate 3
Operator enablement
Who said it may run here. The only gate a machine cannot pass on its own. Enabling is an act with an actor and an audit row.
Withheld entries are not merely hidden — a disabled or non-conforming entry is absent from the readable document entirely.

What Gate 2 does not cover — say it out loud

Signing the manifest is not signing the code.
A signature over the manifest proves the pointer is authentic. It says nothing about what remoteEntry.js serves tomorrow. Module Federation makes this worse than usual: hashing the entry chunk SRI-style still leaves every lazily-fetched chunk unhashed.
So this phase buys authenticated provenance of the pointer, with origin-allowlist trust for the code itself. That is a real improvement. It is not “no unauthorised code can run”, and the design should not be described as if it were.

The next gate, deliberately deferred

Phase 6 — immutable signed bundles
The plugin is published as a versioned, immutable bundle to an object store we control; its digest is signed; the shell loads only from that store. This is what actually binds the code rather than the pointer.
Needs a publishing pipeline, storage and a release flow per plugin — a phase in its own right. Ship provenance now, design toward bundles: verbatim signed bytes and a publisher-key table are the parts that carry over unchanged.

Revocation — the fan-out the current write path does not have

Disabling a publisher key must re-evaluate every entry that key signed, not just stop accepting new ones. Today Apply touches one entry per write and raises the revision by one; a key revocation touches an unbounded set in a single revision. Worth designing before it is needed, because it is the one operation in the whole trust model with no per-entry actor.
Verification is server-side by design. Browser-side checking is mostly theatre — the verifier arrived from the same origin as the code it would be checking. It earns its keep only in the bundle model, where the digest and the signature are fetched independently.
