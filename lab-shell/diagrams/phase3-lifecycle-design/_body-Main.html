App Shell · Phase 3 design

Boot sequence and change propagation

First paint is bounded by the shell's own bundle. No remote chunk is fetched before it, and none is fetched by the registry read — BR-AS08 holds.

Boot

1 · Bootstrap
Shell bundle only. No network, no credential.
→
2 · Index built-ins
Nav tree and route table placed. Zero remote chunks fetched.
→
3 · FIRST PAINT
The shell is usable. Nothing downstream can delay it.
→
4 · NATS connect
Credential minted by the same path the Admin, Refdata and Seafreight apps already use.
→
5 · Registry read
api.* request/reply. Revision reconciled; curated, preloaded and enabled dynamic entries admitted.
→
6 · First navigation
Only now is a remote fetched — pluginLoader decides when, at most once.
Preload is registration, never loading. A preloaded entry reaches the shell through step 5 like any other curated entry; the loader seam is untouched. A static plugin whose remote is down is a red dot and an inline error panel on click — never a blank shell.

Steady state — push, not poll

notify._platform.registry.frontend-plugins.changed
Published on every accepted write. Already implemented — nothing subscribes to it today.
↓
Shell performs a conditional read
The message carries a revision and nothing else the shell trusts. If the revision already matches what it holds, the read is a no-op.
↓
Diff → place, offer, or dispose
Additions indexed live. Static removals offered as a reload. Dynamic removals disposed.

The rule to write down first

The notification is a hint. The read is authoritative.
Core NATS is fire-and-forget: a shell that is disconnected, backgrounded or reconnecting misses messages with no gap detection. So on every reconnect the shell re-reads unconditionally. Without that rule, a shell offline for one minute is silently stale forever — a worse failure than the poll it replaced, because nothing detects it.
