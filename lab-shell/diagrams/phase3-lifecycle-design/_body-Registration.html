App Shell · Phase 3 design

Three ways in, one source of truth

Every path runs through the same Apply — allowlist, revision, audit. There is no second store and no boot-time file the service trusts over its own rows.

1 · Operator curation

Admin UI upsert
If-Match on the held revision → 409 on a stale write, 428 with no revision at all.
Audit actor admin. Disable, never delete.

2 · Preload seeding

Seed file read at service start
Inserts only ids the store has never seen, through the normal write path.
Audit actor preload. An entry the operator has since edited or disabled is never reverted by a restart — which is decision 24's whole objection, answered.

3 · Service announcement

Service publishes a signed manifest on start
Verified server-side against the trusted-publishers table before anything is stored.
Audit actor is the publisher key. Recorded as announced — stored, and served to no shell.

The gate

Announce ≠ activate
A service may say “I exist, here is my manifest, here is my signature.” It may not say “put this in every operator's browser.” A new id is a one-click approval; an id the operator has already enabled comes back on its own after a restart, with no human in the loop.
Changed remote URL on an enabled id
Auto-follow within the same origin; re-approve across origins. Deploys stay quiet, substitutions do not.
BR-AS21 relaxes, it does not disappear. “No self-registration by any transport” becomes “self-registration permitted with a verified publisher key, and never self-activation.”
↓

Registry — service state

Postgres
Source of truth. Signed manifest bytes stored verbatim; the columns are a derived projection for querying and display.
Schema consequence: today the service reassembles the document from columns, and any reassembly invalidates a signature. Cheap to change now, expensive after Phase 3.
